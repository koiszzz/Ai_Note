# 把一个巨型 AI 生成的拉取请求变成可评审的堆叠

## 摘要

- 回顾上一个交付的大功能：你把它塞进一个巨型 PR，还是拆成更小范围 PR？多年来你被迫在"大到评审成噩梦的 PR"与"必须手工同步、解缠冲突的小 PR 链"之间选择；编码智能体放大了做此选择的需要（Gartner 预测 2028 年前每个 SDLC 阶段生产力提升 50%）。
- 典型巨型 PR 内容：新数据模型与种子数据、API 路由与验证、客户端接线与 UI 及空/回退/错误状态——全部在一个 1000+ 行 diff 里；大 PR 变难评审——就……搁置；评审者失去上下文、反馈质量下降、合并更慢、最终低评审交付。
- GitHub 堆叠 PR：原则是分解——把功能拆成逻辑层并识别依赖链；大 PR 变成小的、逻辑有序的 PR 堆叠，每个限定单一关注点、小到评审者能装进头脑、上下文自然从前一个已评审 PR 流来。
- 示例堆叠结构（购物助手加产品搜索）：L1 feat/catalog-data（带种子数据、验证与数据访问模块的带类型目录，基于 main）；L2 feat/search-api（验证的 /api/products/search 端点，基于 L1）；L3 feat/chat-grounding（聊天调用 API 并从真实产品数据回答，基于 L2）；L4 feat/grounded-ui（产品引文卡片与状态，基于 L3）——数据、API、接线、UX 独立关注点，可分配不同评审者。
- 工具链：gh extension install github/gh-stack（CLI 扩展）；gh skill install github/gh-stack 或 npx skills add github/gh-stack（教智能体堆叠）；每层用专门智能体（数据建模智能体、后端智能体、前端智能体）。
- 工作流每层：调智能体 → gh init stack / gh stack add 建层（基为下层）→ 检出、工作、跑验证 → 全绿则提交该层否则迭代；评审者每层关注点（L1：类型对、数据验证、查询助手安全；L2：输入验证、响应契约稳定、错误/空状态；L3：每个答案追溯到真实 API 响应、API 失败或空返回时怎么办；L4：每个引文链回真实产品、加载/空/错误状态全覆盖）。
- 提交堆叠：gh stack push 推分支，gh stack submit 建相互链接的 PR；GitHub 上每 PR 顶部有堆叠图（栈内一键导航）。
- 评审与更新：堆叠图是评审者指南针——阅读自上而下（先了解目标），评审自下而上（每层实现只有理解前层才有意义）；底层变更请求 → 交给拥有分支的智能体 → 修改测试提交推送 → 因分支乱序推送 GitHub 标记"栈中分支已分叉，必须变基"并阻止合并。
- 变基注意：网页端一键 Rebase stack 按钮在 GitHub 服务器上运行变基——提交者重置为点击者、提交不签名、若分支保护要求签名提交会静默破坏；更安全的终端做法 gh stack rebase 本地级联变基（用你自己的 Git 配置交互解决冲突）再 gh stack push；最后 gh stack sync 一次同步整个栈。
- 结论：不再看单个 1720+ 行的 PR，评审可分布在堆叠中小的、自包含目标。

## 正文

以下是文章全文翻译。

想想你交付的上一个大功能。诚实点。你把它塞进一个巨型拉取请求，还是拆成更小范围的拉取请求？多年来，你默默地在两个选项间决定：看着 PR 长到评审成为噩梦，或者把它拆成需要你照料、手工同步、每次下方引入变更都要解缠冲突的小 PR 链。两个选项都有权衡。一个难评审，一个难维护。你当天的决定倾向不那么痛苦的那个。现在加入编码智能体。它们极其高效，据 Gartner 预测到 2028 年将在每个 SDLC 阶段驱动 50% 生产力提升。但它们不能替你拿走如何组织 PR 的选择。它们放大了做选择的需要。

**细看：给购物助手加产品搜索。** 假设你发出给购物助手加产品搜索的提示，走开几分钟后回来评审、引导与批准。但仔细看单个 PR 里往往落了什么：新数据模型及其种子数据；API 路由及其验证；客户端接线与 UI 及空/回退/错误状态……所有这一切甚至更多在一个巨大的 1000+ 行 diff 里。对主要按多年来代码传统写法训练的智能体，此模式是它们默认的交付方式。让我们演出来。你想在现有 web 应用上加产品搜索，起点是：mock AI 助手（从随机行生成器回复）、硬编码散落组件的不一致产品数据、无目录模块、无 API、无数据层——什么都没有。为实施该功能开了 issue，典型流程是建功能分支、分配给编码智能体（或多个自定义智能体）、得到整个实现代码初稿与更新测试……你读代码（好吧，你也许读了代码）。然后仍需手动验证功能行为并做必要更新、推送、用冗长浅薄的 AI 生成描述开 PR、确保 CI 检查绿、自评审 diff 然后请求评审者。你开始了……评审者：改了 1,721 行！！这个描述没多大帮助。我晚点再评审。接下来是熟悉的：大 PR 变难评审——它就……搁置在那里；评审者失去上下文、反馈质量下降；合并更慢。这开启一个手动、凌乱、耗时、容易冲突的过程，功能最终低评审交付。

**GitHub 堆叠拉取请求。** 堆叠 PR 引入不同且更好的交付结构。原则简单：分解。不是追求一个完整解决 issue 的 PR，你把功能拆成逻辑层并识别依赖链到达期望目标。这给你与你的智能体一种原生方式，把原本落进巨型 PR 的工作分解为小的、聚焦的、可独立评审的层。那个难评审的大 PR 变成较小的、逻辑有序的 PR 堆叠，每个限定单一关注点、小到评审者能装进头脑，上下文从前一个已评审 PR 自然流动。

**堆叠结构。** 先且重要：设置堆叠基。这重要，因为整个堆叠管理生命周期中的 CI 检查与合并规则都相对堆叠基评估。然后识别核心基础工作单元放在靠近基处（堆叠最低），把依赖工作分层其上。示例堆叠：L1 (feat/catalog-data) 带种子数据、验证与数据访问模块的带类型目录，依赖 main（堆叠基）；L2 (feat/search-api) 验证的 /api/products/search 端点，依赖 feat/catalog-data；L3 (feat/chat-grounding) 聊天调用 API 并从真实产品数据回答，依赖 feat/search-api；L4 (feat/grounded-ui) 产品引文卡片+状态，依赖 feat/chat-grounding。独立关注点清晰：数据、API、接线、UX，可为每个分配不同评审者受众——数据由数据所有者评审，UX 由 UI 所有者评审。GitHub 对堆叠 PR 的原生支持可从 PR UI 启动，并经 gh stack CLI 无缝延伸到终端。

安装 CLI 扩展：gh extension install github/gh-stack。古时候你就能开工了。今天不行，有智能体与你并肩工作。这些智能体需要学堆叠如何工作以及如何代表你创建与管理它们。gh-stack 技能教它们这个：gh skill install github/gh-stack，或 npx skills add github/gh-stack。对上面示例的特定功能，你的开发工作流有自定义智能体，各带定义的工作流并遵循严格范围纪律以实现小而单一范围 PR 的目标：L1 数据建模智能体、L2 后端智能体、L3 前端智能体、L4 前端智能体。设置最后一块是确认 CI 存在。如前所述，每个 PR 相对堆叠基评估，这些检查为每层运行。

**第一层：数据目录基础。** 多数智能体工作流今天自动化并在循环中自主执行，但为说明我们逐步覆盖。此时所有智能体都熟悉堆叠 PR 如何工作，此阶段典型工作流：以适当提示调用数据建模智能体；智能体用 gh init stack 初始化新堆叠并设第一个分支 feat/catalog-data（基为 main）；检出、工作、运行验证；（检查全绿）？提交该层：迭代。未来评审者注：类型正确吗？数据验证了吗？查询助手安全吗？句号。

**第二层：产品搜索 API。** 类似流程：调后端智能体；智能体用 gh stack add 在层一之上加下一层 feat/search-api（基：feat/catalog-data）以导入完成的数据访问模块；检出、工作、运行验证；开发者手动测试 API；（API 工作且检查全绿）？提交该层：迭代。评审者注：输入验证了吗？响应契约稳定吗？错误/空状态在此处理还是推给下游？句号。

**第三层：把聊天接到 API。** 下一层：调前端智能体；智能体在层二之上加下一层 feat/chat-grounding（基：feat/search-api），它将带着数据访问模块与验证 API 一起分出分支；检出、工作、用 Playwright 跑浏览器测试；（全绿）？提交：迭代。评审者注：每个答案都追溯到真实 API 响应吗？API 失败或返回空时怎么办？句号。

**第四层：接地 UI 与引文。** 你会注意到层三与层四虽作者相同（前端智能体）却分层分明。这是刻意的。UI 所有者不应检查底层数据流，反之亦然，此结构允许这种独立性。前端智能体：用 gh stack add 在层三之上加下一层 feat/grounded-ui（基：feat/chat-grounding）；检出、工作、Playwright 浏览器测试；（全绿）？提交：迭代。评审者注：每个引文链回真实产品吗？加载、空与错误状态全覆盖吗？句号。

**提交堆叠。** 四个本地堆叠分支就绪。下一步 gh stack push 推送到远程，然后 gh stack submit 在 GitHub 上创建相互链接的 PR。

**堆叠图与每层 CI。** 切到 GitHub，四个 PR 打开，每个顶部有堆叠图——栈内 PR 间的一键导航系统。

**评审与更新堆叠。** 该换帽子看评审者穿越堆叠 PR 的旅程。堆叠图是评审者指南针——顶部与底部之间朝向成功合并的导航辅助。移动有方向：自上而下阅读，自下而上评审。自上而下阅读求上下文：评审过程一开始就给你最终目标，能设定方向。"哦，所以我们想在聊天界面显示产品卡片。"自下而上评审建立在预定检查点上：每层实现只有理解前层才有意义。你不再看单个需一次坐定评审的 1720+ 行 PR，评审可分布在堆叠中小而自包含的目标上。作为分配的人在环评审者，你进来看层一（堆叠底部 PR），看到自动 Copilot Code Review（CCR）抓住两个你同意该修的问题。底层请求变更，因此你：把反馈交给层一作者（拥有分支的数据建模智能体）；建议被应用、测试、提交并推送；修复落在 feat/catalog-data 后，自然下一个问题是：对层二、三、四意味着什么？由于 feat/catalog-data 分支在评审后乱序推送，GitHub 明确标记："此堆叠中一些分支已分叉，必须变基"，并配"无法作为堆叠合并"标志，阻止合并。回到 GitHub PR UI，出现一键 Rebase stack 按钮。用前有重要须知：用此按钮触发网页变基在 GitHub 服务器上运行——重置提交者为点击者、结果提交不签名、若分支保护要求签名提交，这一击静默破坏。更安全等价的终端做法是 gh stack rebase 在本地执行同样的级联变基（你交互解决冲突，但用你自己的 Git 配置），然后 gh stack push。最后，你将贯穿堆叠传播。堆叠其余部分（本地与 GitHub 上）现在需要追上，没有比单条同步命令 gh stack sync 更容易的了。一体化流程从 origin 获取、把 feat/catalog-data 之上每个分支级联变基到新提交、推送变基分支并从 GitHub 同步 PR 状态。这样变更向上涟漪，无人手工触碰层二、三、四。回到 GitHub，所有检查重跑、通过，堆叠图落回从 main 到 feat/grounded-ui 的干净可合并线。
