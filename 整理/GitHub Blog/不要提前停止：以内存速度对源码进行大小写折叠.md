## 摘要

- 用户搜索 café 而语料含 CAFÉ，或输入 Straße 而存储的是 STRASSE：需要消除大小写差异的规范形式（大小写折叠）才能视为匹配；它出现在一切"匹配而非显示"文本的地方：搜索引擎、正则 (?i) 标志、不区分大小写的用户名与主机名。
- 规模背景：GitHub 代码搜索引擎 Blackbird 索引超 1.8 亿个仓库（超过 480TB 源码）；每个字节在提取 ngram 前都折叠，每个潜在查询结果还需要另一次折叠。该规模下即使基础操作的速度也开始重要。
- 反直觉核心：ASCII 快速路径的最大胜利来自移除一个优化而非添加一个——无分支扫过整个缓冲区比在首个非 ASCII 字节提前停止更快；结果以 Rust crate casefold 开源。
- 折叠不是小写化：小写化用于显示、区分区域设置与上下文；折叠用于比较，刻意上下文无关与区域无关；Unicode 字符数据库提供显式 CaseFolding.txt。crate 只实现简单（1 对 1）折叠（状态 C 与 S），不实现多字符"全"折叠或突厥区域折叠。
- 分支即敌人：带 break 的朴素循环约 3.1 GiB/s；删除所有分支（OR 累积高位检测非 ASCII + 算术范围测试 + 位 5 设置）后循环无数据依赖控制流，可被 LLVM 向量化（NEON 16 字节/次），达 45+ GiB/s（约内存带宽）。
- 测量阶梯：带分支朴素 3.1 GiB/s（0 向量指令）→ 无分支写/保留 break 2.6 GiB/s → 去掉早退 break 7.6 GiB/s（25 向量指令）→ 完整无分支 >45 GiB/s（41 向量指令）；早退本身阻止向量化，无分支写只在向量化后有价值（标量中反为劣化）。
- 避免堆分配：简单折叠原地处理 ASCII（OR 累积器高位清则原缓冲直接返回）；需要第二缓冲的唯一原因是个别折叠使字符串变长（U+023A Ⱥ 与 U+023E Ɀ 从 2 字节折叠为 3 字节字符），一次分配最坏情况容量（输入 1.5 倍）。
- 让 Unicode 也廉价：1484 个简单折叠映射压缩到 1776 字节——64 码点"页"位图（负测试单比特拒绝）+ 累计 popcount 侧表 + 区间压缩（238 条运行，每条两个干净字节）+ 小端字节加法折叠（字节空间算术，免解码免编码）。
- 对照：简单折叠 ASCII 超 45 GiB/s，比 str::to_lowercase 快 50%+；CJK 无折叠 2.95 GiB/s；全折叠最坏 869 MiB/s；长度变化折叠 1.26 GiB/s；HashMap 在所有负载垫底。相对朴素表（约 11.6 KB）、regex-syntax（约 70 KB）、Go unicode.SimpleFold（约 7.3 KB）、HashMap（约 17 KB），本 crate 仅 1776 字节。
- 两课：无分支全缓冲扫描胜过提前停止；字节空间算术折叠胜过解码到码点。

## 正文

以下是文章全文翻译。

假设用户搜索 café，而你的语料包含 CAFÉ；或者他们输入 Straße，而你存储了 STRASSE。要让这些算作匹配，你需要一个消除大小写区分的规范形式，使两个只在大写上不同的字符串比较相等。这种形式就是大小写折叠（case folding），它出现在一切"匹配文本而非显示文本"的地方：搜索引擎、正则 (?i) 标志、不区分大小写的用户名与主机名。这是基础操作，但在 GitHub 我们大量运行它。Blackbird（GitHub 的代码搜索引擎）索引超 1.8 亿个仓库——超过 480TB 源码。每个字节在提取 ngram 并构建索引前都被折叠，且每个潜在查询结果还需要另一次（隐式或显式的）折叠来定位匹配。在该规模下，即使基础操作的速度也开始重要。这篇文章讲我们如何让它变快，起点有些反直觉：ASCII 快速路径最大的胜利来自移除一个优化而非添加一个。事实证明，无分支扫过整个缓冲区比在第一个非 ASCII 字节提前停止更快。我们把结果开源为一个名为 casefold 的 Rust crate。

**折叠不是小写化。** 小写化用于显示，区分区域设置与上下文：希腊语词末 sigma 在词末小写为 ς、别处为 σ，土耳其语 I 的小写与英语 I 不同。折叠用于比较，刻意上下文无关、区域无关。要点是保持稳定且对称的关系，使 A 折叠匹配 B 时、B 在任何区域都折叠匹配 A。Unicode 字符数据库为此发布显式 CaseFolding.txt。两种操作在真实字符上分道扬镳——ß、İ、词末 sigma——这就是用 lowercasing 替代会静默产生错误匹配的原因。本 crate 只实现简单（1 对 1）折叠——CaseFolding.txt 中的状态 C 与 S——不实现多字符"全"折叠（ß→ss）或突厥区域折叠（带点 İ）。这不是不寻常的选择：ripgrep 等常用工具与正则引擎做同样限制，跨工具一致很重要。

**反直觉核心：不要提前停止。** 我们主要处理源码，因此要折叠的文本绝大多数是 ASCII，让它以内存速度运行是我们能做的最重要的事。其他一切只需不让罕见非 ASCII 路径破坏它。ASCII 字母的折叠平凡（A..=Z 映射到 a..=z，其余不变），因此 ASCII 遍实质就是"扫缓冲区，原地小写"。让任何 LLM 写它，你可能会得到：逐字节迭代，若 *b >= 0x80 则 break 把剩余交给 Unicode 路径；is_ascii_uppercase 则 *b += 32。它看起来理想：做廉价字节工作，遇到非 ASCII 立即 break。在 Apple M4 上这运行约 3 GiB/s。孤立看还行，但比"最优"差 15 倍多，因为 if 分支。让我们逐行删除每个分支：`if b >= 0x80 { break }`→根本不停止，把每字节 OR 进累加器、循环后测一次（high_bit_acc |= *b）；`A..=Z` 范围测试→改为算术 `b.wrapping_sub(b'A')`。剩余循环体内无分支、无早退：`high_bit_acc |= *b; let is_upper = b.wrapping_sub(b'A') < 26; *b |= u8::from(is_upper) << 5;` 循环后若 high_bit_acc & 0x80 == 0 则直接返回（纯 ASCII 已原地折叠，无需第二缓冲）。无数据依赖控制流的循环平凡可向量化：LLVM 发出 16 字节 NEON，整体运行 >45 GiB/s——基本是内存带宽。

每步贡献多大？纯 ASCII 上的累计阶梯测量（Apple M4，5.7 KB 缓冲）：朴素（break+分支测试）3.1 GiB/s（0 向量指令）→ 无分支测试/写、保留 break 2.6 GiB/s（0）→ 去掉早退 break 7.6 GiB/s（25 向量指令）→ 无分支测试+写 >45 GiB/s（41 向量指令）。早退是阻碍向量化的闸门：保留 break 但让体完全无分支，仍得到零向量指令（约 2.6 GiB/s）；数据依赖循环退出本身足以让循环保持标量。只有去掉 break 编译器才能向量化。最后一步——让大写折叠无分支——再把部分向量化循环（约 7.6 GiB/s）变成达到内存带宽的直线算术。注意：无分支在标量代码中是劣化。看表：保留 break 时把体做成无分支（2.6 GiB/s）实际慢于朴素分支循环（3.1 GiB/s）。汇编解释原因：分支版只在真正改变字节时才存储，其条件 strb 对每个小写字母、数字与空格（真实文本的绝大多数）跳过，且守卫它的预测良好分支几乎免费；无分支版用无条件 strb 替换少取存储，每次迭代写回全部约 5,700 字节而非少数大写字节。为无收益付出额外写流量。无分支写只在循环向量化后获胜，因为那时存储变成单个 16 字节向量写，每字节成本消失。教训：无分支体只作为向量化的使能器才值得；标量代码中单独使用可能让你吃亏。

还有中间地带，标准库使用它：`[u8]::is_ascii` 一次扫描一个机器字（64 位目标每次迭代测 16 字节，OR 两个 u64 通道并用单个 & 0x8080_8080_8080_8080 掩码检查全部高位）。可在其上构建 ASCII 快速路径：块扫描找 ASCII 前缀，再对其运行无分支（可向量化）转换。它保留早退能力，同时让两半都快。代价是数据读两次，落到约 23 GiB/s——约单遍无分支扫描的一半，约朴素 break 循环的 7 倍。坚实、通用的默认；但当你控制整个循环并能把检测与转换合并进单次无分支遍时，不是绝对上限。融合两遍会更快吗？保持分块早退但每 16 字节块确认 ASCII 后立即转换，只读一次数据。实测约慢 2.6 倍（8.7 GiB/s 对两遍 23）。内部块转换仍向量化为单个 16 字节操作，但每个 16 字节现在有数据依赖早退分支，把循环钉在每次一块：编译器不跨块展开或软件流水，每次迭代付完整 load→test→branch→convert→store 延迟。拆成两遍，每遍干净：扫描是无分支轻、无存储的字扫描，转换是完全向量化的无分支扫描（>45 GiB/s）。两遍快无分支胜过一遍有分支融合——即使融合版触碰数据次数减半。同样的教训再来一次：热循环中，分支是敌人。

**避免堆分配。** 45 GiB/s 也意味着零不必要分配。simple_fold 按值取 String，拥有它可原地修改并返回的堆缓冲。若 OR 累加器高位清，输入是纯 ASCII 且已原地折叠，直接把同一分配交回，无第二缓冲无拷贝。否则 memchr 到首个非 ASCII 字节并从那里扫描尾部，输出缓冲保持未分配（空写游标）直到遇到折叠为不同字节的字符。多字节内容从不折叠的文本（CJK、韩文、假名、阿拉伯文、希伯来文、符号）也原封不动返回原始分配，从不拷贝一个字节。为何用第二缓冲而非像 ASCII 遍那样原地重写？因为折叠可使字符串变长：几乎所有折叠保留或缩短 UTF-8 长度，但两个异常增长——U+023A（Ⱥ）与 U+023E（Ɀ）各 2 字节却折叠为 3 字节字符（ⱥ、ɀ）。一旦出现，输出不再适合输入字节，需要新写入处。我们一次分配该缓冲，按最坏情况定大小，而非随更多折叠增长。增量 reserve 调用意味着重新检查容量、偶尔重新分配、拷贝已写内容、处理额外长度/容量簿记；一次性前置分配让裸写游标直线跑到底。游标在首个增长/变化折叠前为 null，兼作"是否已分配额外缓冲"标志。定大小需要增长界，那两个异常给出：每 2 输入字节至多 3 输出字节，输出上限输入 1.5 倍——正是预留容量。之后循环经裸指针无容量检查写入，结束时调用一次 set_len。另两个细节保持分支轻：两次折叠之间的不变字节运行用单次 copy_nonoverlapping 移动；每次折叠无条件写小端字全部 4 字节再只按折叠长度（1–4）推进游标——从热路径去掉输出长度分支，预留中的 +4 作为最终字符过度存储的安全余量。

**让 Unicode 也廉价。** 字符确实折叠时，我们仍不想掉下悬崖——解码 UTF-8、哈希查找、重新编码。Unicode 16.0 有 1484 个简单折叠映射，但它们是极稀疏且结构化的关系。四个观察把它们缩到 1776 字节并让折叠无需解码完整字符即可运行。即使非 ASCII 路径上，绝大多数字符不折叠。热操作不是"折叠这个字符"，而是"这个字符折叠吗？"几乎总是否。表必须让负测试尽可能廉价；实际折叠是罕见路径上更罕见的情况。这就是 HashMap<u32,u32> 是错误形状的原因，不只是更大的问题。哈希表为命中优化：约一次探测找到存在的键；但我们的负载由未命中主导——根本不在表中的字符——而未命中是哈希表最不喜欢的查询：仍需哈希键、跳到桶、走探测序列足够远以证明不存在。

**可折叠码点聚成 64 码点"页"。** 可折叠码点成团。把码空间切成 64 码点"页"，约 1484 个折叠只触及约 1960 个可能页中的 59 个。每页一位的存在位图单独回答负测试：清除位是确定性的"无折叠——拷贝通过，完成"，使无折叠脚本廉价。只有置位时咨询第二结构：累计 popcount 侧表对页排名（前面有多少填充页）以找到其条目切片，约 1900 个空页不存任何内容。word_idx 只依赖首字节（四字节序列还依赖第一续字节），因此位图加载可提前发出。

**页内折叠成运行。** 置位页位告诉我们此页有折叠，但不告诉哪些码点或折叠成什么。明显编码是每个可折叠码点一条目——但既笨重又难搜：页可含几十个折叠，得全扫找匹配当前码点的。数据结构再次救场。相邻码点压倒性地共享到其折叠的相同 delta：A–Z 全映射 +32，Latin Extended 满是交替运行如 0x0100、0x0102、0x0104……每第二个码点折叠。我们存运行（start、end、stride、delta）而非逐码点条目，1 位 stride 标志覆盖连续与隔一情形。此区间压缩把约 1484 个折叠塌缩为跨 59 页仅 238 条运行（每页约四条），页内搜索只需看少数条目。范围加 delta 编码（含 stride 技巧）借自 Go 的 unicode 包，其 CaseRange 记录存 Lo/Hi 范围加逐大小写 delta，UpperLower 哨兵标记交替块。运行在页边界拆分，使运行从不跨两页。

**运行记录是两个干净字节。** 两端点在同一页内可装入 6 位，跨两个数组拆分：RUN_END_LOW[i] = end & 0x3F（扫描键），RUN_START_STRIDE[i] = (start & 0x3F) | ((stride−1) << 6)（命中才读）。因每个键是一个干净字节，页内搜索可宽化：不逐条比较 cp & 0x3F 与运行，而是把 8 个 end_low 字节装入单个 u64 并用一个无分支 SWAR 步全测——(chunk | 0x80…80) − broadcast(low) & 0x80…80 为每个键 ≥ cp & 0x3F 的通道置顶位。对掩码做单次位扫描（键已排序，首个置位通道即所需运行）找到槽位。页平均约 4 条运行；那一次 8 宽比较几乎总是单步解决整个搜索。一个不幸的页确实有 30 条运行，把比较放进每步跨越 8 个键的短循环——但该循环在整个 Unicode 中恰好一页上最多触发几次，且从不在常见页上。无论哪种：无逐运行分支，任何地方都无码点重建。

**折叠是小端字节加法。** 小端机器上，折叠字符的 UTF-8 字节读作 u32 等于源字节（u32）加每运行常量。并行 BYTE_DELTA[i] 表把整个折叠变成掩码加载、一次 wrapping_add 与 4 字节存储。两个长度——源字符的 length_mask 与目的按折叠长度推进——来自另一个小技巧：UTF-8 序列长度由其首字节高四位固定，使 16 个可能长度各装一个 nibble 进单个 64 位常量（0x4322_1111_1111_1111）；长度即移位与掩码，(LEN_BITS >> (4 * (lead >> 4))) & 0xF——无 if 链、无表内存、无预测器可猜错的东西。按折叠长度推进甚至处理长度变化折叠——U+212A 开尔文符号（3 字节）→ k（1 字节），或 U+023A Ⱥ（2 字节）→ U+2C65 ⱥ（3 字节）——写更少或更多字节。这是我们相信真正新颖的部分：我们看过的每个其他折叠器——ICU、Go unicode、Rust regex、CPython、glibc——都解码 UTF-8 到码点、在那里应用折叠、再重新编码（连 SIMD 折叠器都先解码）。在字节空间做算术跳过解码与编码，这正是该路径能跑赢已制表的哈希表的原因——哈希表仍须解码键并编码结果。字节空间算术假设输入是良构、最短形式 UTF-8；超长编码（如 / 编码为 0xC0 0xAF）有不同的字节模式，会破坏 length_mask 与 delta 算术。这在 Rust 中不是真限制（&str/String 保证有效 UTF-8），但别处喂裸字节的调用者必须验证。

**尾部循环的 ASCII 捷径。** 第一遍已小写每个 ASCII 字节，因此扫描在尾部遇到 ASCII 字节时只推进单字节——无页探测、无表触碰。且不拷贝该字节：未修改字节（ASCII 与不折叠多字节）不被逐个移动；扫描只走到真正折叠的字符，然后用单次 copy_nonoverlapping 刷新上次折叠与本次之间整段不变运行。混合文本（CJK 加 ASCII 空格标点）因此快速穿过 ASCII 填充，只对真正多字节字符查位图，批量拷贝而非逐字节。

**整合：整张表。** PAGE_BITMAP 248 字节、POPCNT_SAMPLES 32、PAGE_OFFSET 60、RUN_END_LOW 246、RUN_START_STRIDE 238、BYTE_DELTA 952，总计 1776 字节。每个折叠条目 9.6 位，其中一半以上是换取无解码路径的 BYTE_DELTA 侧表；索引+运行记录本身约 4.4 位/条目。对照替代：朴素 [(u32,u32);1484] 约 11.6 KB、regex-syntax 的 case_folding_simple 约 70 KB、Go unicode.SimpleFold 约 7.3 KB、运行时 HashMap 约 17 KB——本 crate 1776 B，小一个数量级以上，且大多不解码字符。

**相对替代方案的表现。** 常见情形 ASCII 上，折叠以内存带宽运行（>45 GiB/s），领先其他真实折叠器一个数量级以上，比（不等价的）str::to_lowercase 快 50%+。非 ASCII 情形的粗略"上界"：用 simdutf crate 测量优化 UTF-8 解码+编码往返（不做实际折叠），约 2 GB/s，只比我们全折叠最坏输入快约两倍。朴素哈希表在所有负载垫底。负载表（输入大小）：纯 ASCII（5.7 KB）simple_fold >45 GiB/s、simd_normalizer 1.21 GiB/s、HashMap 213 MiB/s；中日韩无折叠（8.1 KB）2.95/1.97/558；符号/缅甸文无折叠（9.0 KB）2.96/1.56/410；最坏全折叠（8.8 KB）869/922/334 MiB/s；长度变化折叠（1.7 KB）1.26 GiB/s/716/233。绝对数字仅供参考：整个设计依赖自动向量化、SWAR 与小端字节算术，数字甚至行间比率会随微架构大幅变化。

**带走的两点。** 大小写折叠是文本操作中最基础的操作之一，这正是它值得努力的原因：我们索引的每个字节都经过它。胜出来自两个都逆直觉的想法——无分支扫整个缓冲区而非提前停止；把折叠做成字节空间算术而非解码到码点。两者结合让常见情形以内存带宽运行、罕见折叠无需解码，表小到（1776 字节）常驻。无解码的字节空间折叠是我们相信真正新颖的部分；它正是该路径能击败已有答案的哈希表的原因。crate 是 casefold；生成表与完整设计说明随源码一起。
