# 框架就是一切（大致如此）

## 摘要

- 作者观点：被 AI 淹没时，少即是多——真正带来生产力收益的不是安装、配置或骗智能体做什么，而是如何使用框架（harness）与多好地理解它；GitHub Copilot 即智能体框架（harness），文中两者互换使用。
- 步骤 1 选工具：GitHub Copilot 家族内有很多选择（CLI、新 Copilot 应用、VS Code、Visual Studio、JetBrains）；体验日益集中到同一框架上，学一次框架处处可用；新手推荐 CLI（终端界面即文本，无 UI 学习成本）。
- 步骤 2 开启 YOLO 模式（Allow All）：让智能体无需询问即可执行任何命令；智能体需要自主性才能带来生产力提升，反复点"Approve"只训练你不读内容、违背目的；但 YOLO 模式不要在本地机器运行智能体（组织数据私有、错误代价高），用 GitHub Codespaces 或开发容器沙箱。
- 步骤 3 从原型开始：AI 神奇之处在于可提前轻松原型化一切；如日期选择器 web 组件——让 AI 生成 20 个 mock 放一个 HTML 文件比较；人类处理感官丰富模型（图像、形状）比密集文本快得多；非视觉任务也适用——创建 API 端点前先做可视化 mock（Mermaid 图）理解需求与约束；建议用中型模型（GPT 5.6 Terra 或 Claude Sonnet）中等推理，特征/bug/增强期间坚持同一模型以享受提示缓存折扣。
- 步骤 4 有条理地规划：切换 plan 模式（不新开会话），/plan 构建日期选择器；提示模糊没问题，规划正是为此——让模型问你本会自问的所有问题（起止日期可否相同、部分选择有效吗、可清除吗、"今天"总可见吗、允许手动输入吗、日期存储格式、允许粘贴吗）；可用 Matt Pocock 的 grill-me 技能让规划更激进；规划关键是深入参与问题并引导模型，不盲目接受每个建议。
- 步骤 5 用 Autopilot 实现：内置循环强制模型继续工作、确保真做了它说会做的每项计划；Copilot 自动编排——读文件用小型模型的 Explore 子智能体，复杂动作选大型模型的 General Purpose 子智能体；子智能体与多模型工作流开箱即用。
- 步骤 6 人工评审与迭代：模型不能读心、会出错，迭代直到得到真正想要的；别满足于"够好"，对质量毫不留情；审美与品味决定最终产品质量（作者用 CSS 框架 Postrboard 作技能给模型设计指导）。
- 步骤 7 橡皮鸭结果：请求 Rubber Duck 评审——Copilot 从不同 AI 家族请求评审（用 GPT 5.6 Terra 会请求 Sonnet 评审），不同模型盲点不同；可用于工作流任何点；可与 Autopilot 组合循环改进；此步多花 token 但真正锤炼代码。
- 步骤 8 收获：暂存提交或继续下一个功能；建议为无关后续工作开新会话（会话视作主题性的）。
- 核心信息：现在 AI 领域没人真正知道自己在做什么，今天的魔法咒语会是明天的反模式；专注用最简单方式获得可重复、高质量结果，学好框架就够。

## 正文

以下是文章全文翻译。

如果你现在对 AI 感到不知所措，你不是一个人。似乎每天都有新工具、新 MCP、新模型、新技能、新工作流、新功能、新社交帖子，某种"嘿快看！我用这一个奇怪提示完全搞定了 AI"的形式。我……不信你。我每天与 AI 共事，我发现的是一点远比多点好。真正起作用的不是我安装、配置或骗智能体做什么。那东西有趣，但归根结底感觉像噱头。我生产力最大的收益来自我如何使用框架以及多好地理解它。所以在这篇文章里，我分享一个简单的、只用 GitHub Copilot 现有功能就能大幅提升 AI 效能的简单工作流。没有奇怪提示。没有别人似乎都知道的技能。只有框架。框架就是一切——大致如此。

**免责声明。** 我把"框架"与"GitHub Copilot"互换使用。本文目的是保持简单，只需知道 GitHub Copilot 是一个智能体框架。我不是暗示你永远不需要任何技能、MCP、指令或自定义智能体。事实上，随着你进步、需要定义复杂工作流并为团队自动化，那些东西会变得相当重要。我在这篇博客里就用了几个！我在此指出的是：不需要任何那些东西也能在 AI 上非常成功。还有，外面有很多垃圾。不信就问智能体创建一个做任何事的技能。它会欣然照办。那个生成技能是否真能用，它都能轻松发布到任何技能或 MCP 注册表。

**1. 选个工具，任何工具。** 这很明显对吧？选工具！太简单了！但即使在 GitHub Copilot 家族内也有许多选项：CLI、新 GitHub Copilot 应用、VS Code、Visual Studio、JetBrains，仅举几例。好消息是这些体验日益集中到同一框架上。细节因工具而异，核心工作流一致。学一次框架，处处使用。话虽如此，我确实相信学框架是关键，学它最好方式是最贴近它。所以如果你刚开始，我建议从 GitHub Copilot CLI 开始。它是终端界面，意味着只是文本。没多少 UI 要学。你输入提示。智能体做事。但交互更直接、即时、老实说非常令人满足。本演示我用新 GitHub Copilot 应用，但它用的框架与 CLI、VS Code 及许多能找到 GitHub Copilot 的地方完全一样。

**2. 开启 YOLO 模式。** YOLO 模式又称"允许全部"，让智能体无需询问执行任何命令。这因所用工具而异，多数只是聊天中的 /allow-all 命令。否则智能体每次需要干活都会停下来等你批准。智能体需要自主性你才能看到生产力提升。如果每件它做的事都要批准，你不如自己做。而且那是糟糕的用户体验。没人想被贬到桌前整天按"Approve"按钮。反复按"Approve"只是训练你不读被要求批准的内容，违背目的。但你想对智能体保持安全。好人也会遇到坏事。用 YOLO 模式时，不要在本地机器上运行智能体。工作时尤其如此——组织系统上的数据是私有的，错误代价高昂。幸好有一堆在沙箱中运行智能体的选项。容易入门的一个是 GitHub Codespaces 或开发容器。

**3. 从原型开始。** AI 最神奇之处是你几乎可以提前原型化一切。历史上并非如此。原型化曾是项目完整阶段，往往是奢侈品。现在，一个提示就能做一个。看几个例子。假设我们想构建日期选择器 web 组件。看似简单，实际相当复杂。想想你可能想用它做的所有不同事情：组件内如何导航？选中日期长什么样？选中范围长什么样？用户如何在日、月、年之间导航？从简单原型开始并得到几个变体。我通常这样开始：给我 20 个日期选择器 web 组件的 mock。全放一个 HTML 文件里好让我比较。AI 生成了各种不同布局，其中一个 mock 从年视图开始。这很有趣。我希望日期选择器让用户缩放到年、然后月、最后日。这些是你不看到就想不到的东西。作为人类，我们处理感官丰富的模型（图像、形状、可触摸布局）比密集文本快得多。早期做低投入原型帮助复杂概念立刻直观。这也适用非视觉任务。比如想加新 API 端点，我仍会先做视觉原型理解需求与约束再动手实现：创建此项目 API 的可视化 mock。给五个处理新 API 端点（允许用户下载分析数据）的选项。由于 Copilot 应用支持 Mermaid 图，智能体渲染为 Markdown，画出实现此端点的五种方式。与智能体工作时，容易忘记一切都有细微差别。原型化提前揭示细微差别，避免把宝贵时间与 token 花在返工上。我建议多数工作用中型模型（如 GPT 5.6 Terra 或 Claude Sonnet）配中等推理。也建议此特定功能/bug/增强期间坚持所选模型。提示缓存省 token。只要不换模型或推理级别，先前聊天保持与模型缓存，给你未来请求折扣。

**4. 有条理地规划。** 现在你知道实际想要什么与最初以为想要什么，该规划实现了。不新开会话，在 GitHub Copilot 切换到 plan 模式。/plan 构建一个日期选择器 web 组件。我希望用户能缩放进出年、月、日。提示相当模糊，你可能有比我更多上下文，但这只是演示。没有更多上下文也没关系。这正是此步的作用。理论上，你能让模型一击完成任何事——如果你用完美顺序组合完美上下文与完美提示。理论上。但我们没人能做到。规划通过问你手工构建时需要自答的所有问题帮你接近理想：起止日期可相同吗？部分选择有效吗？用户应能清除日期吗？"今天"应总是可见选项吗？允许手动输入吗？日期存储为什么格式？允许粘贴日期吗？清单无穷无尽。你不可能想到所有边缘情况，但模型能帮你识别许多。想让 plan 模式在提问数量与边缘情况上更激进，可安装 Matt Pocock 的"grill-me"技能：/plan /grill-me 构建日期选择器 web 组件……。此规划步骤关键。要点不是让你接受 AI 的每个建议——那样你就否定了规划过程的价值。要点是深入参与问题并引导模型。这是你的专业发挥作用之处。你也可反问模型问题。规划过程即使你打断问澄清问题也会继续。

**5. 用 Autopilot 实现。** 计划完成后，GitHub Copilot 会提示你切到 Autopilot 并开始实现计划。Autopilot 是内置循环。它强制模型继续工作，确保它真做了它说会做的事——此案例中是完成计划每一项。GitHub Copilot 此阶段自动充当编排器。需要读代码库文件时用小型模型的"Explore"子智能体；判定动作相对复杂时，选大型模型的"General Purpose"子智能体。虽可用自定义智能体与指令对编排做细粒度控制，但无需任何特殊操作就能享受子智能体与多模型工作流的好处。它开箱即用，即使你不知这些东西存在。

**6. 人工评审与迭代。** 这是你得到多巴胺的时刻。你看到 AI 创建的东西。但很可能不会恰好得到你想要的。这正常且预期。模型不能读心，而且易错。与模型迭代直到得到真正想要的。无论是纯代码还是改进 UI，这部分你的品味决定最终产品质量。例如，这是 GitHub Copilot 给我的日期选择器。我已经看到它有些问题：动画不一致；悬停选中日期时因颜色对比文本不可读；顶部不需要说"12 YEARS"；点"Today"时在月或年视图不会带我到日。还有我不喜欢设计。看起来太像 AI 做的——因为它就是！所以这里我们进入跟进模式。我用我创建的 CSS 框架 Postrboard。把它加为技能，指向 CSS 并告诉智能体如何使用。给模型一些设计指导很有帮助，通常 CSS 框架就是你需要的。注意这有多对话化。别想太多。修复这类小东西时，直接给模型。有上下文就有提示。最重要是别满足于"够好"的 AI 输出。坚持质量。对此毫不留情。那部分仍是你的责任，知道什么算高质量结果、什么不算，是你带来的价值。没有 AI 会取代你的人性触感与创造力。

**7. 橡皮鸭结果。** 迭代并对成果满意后，该最终评审了。向 GitHub Copilot 请求 Rubber Duck 评审，直接要求即可：对这个日期选择器组件实现执行橡皮鸭评审。Rubber Duck 评审中，GitHub Copilot 从不同 AI 家族请求评审。比如我用 GPT 5.6 Terra，它请求 Sonnet 评审。不同模型在不同数据上训练，因此盲点不同。橡皮鸭评审帮助识别单一模型可能遗漏的潜在问题。注意你可在工作流任何点用它。可橡皮鸭原型、可橡皮鸭计划——取决于你是否想要第二份 AI 评审。想更进一步，可把橡皮鸭与 Autopilot 组合，让模型在循环中协作改进最终结果：/autopilot 橡皮鸭这个日期选择器实现。有结果后仔细评审并做必要调整。重复橡皮鸭评审直到你与评审模型都同意剩余项目收益递减。此步后你会得到比之前更精炼的结果，并可能识别许多额外边缘情况。此步确实花更多 token，但你在真正锤炼代码。把它当作对你未来自己的投资——因为你现在抓住了这些问题，未来不必处理。

**8. 收获。** 此时你准备好暂存与提交，或继续下一个想随此 PR 添加的功能。我建议为任何与日期选择器无关的后续工作开新聊天会话。可把聊天会话视作主题性的；开始偏离主主题太多，大概该新开会话了。我意识到这是个有点人为的例子，但能否都暂停片刻惊叹我们现在能用 AI 完成什么？构建日期选择器曾是你能尝试的最难事之一。简单工作流对多数人足够。简单也助你多任务。保持简单时，更容易推理哪个智能体处于什么状态、你上次在做什么。你的上下文窗口也有限。AI 领域现在发生太多事。你能构建与实验的东西没有上限。可加 MCP 服务器、技能、指令与自定义智能体；可设工作流与循环、创建提示智能体的智能体、搭建整个虚拟开发团队。但记住：现在没人真正知道自己在做什么。我们都在边做边弄清。今天很多 AI 的魔法咒语会是明天的反模式。专注用最简单方式获得可重复、高质量结果。学好框架，你就没问题。
