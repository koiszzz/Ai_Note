# 把跨平台 GUI 应用移植到 Rust

## 摘要

- Firefox 崩溃报告器是主进程崩溃时收集信息并与用户交互的独立应用；本文详述用 Rust 重写崩溃报告器的方法、动机、架构与实现细节。
- 为什么重写：崩溃报告器长期困于"够好"与"维护可怕"的局部最大——3 个独立 GUI 实现（Windows、GTK+ Linux、macOS）、胶水代码（多为 C++ 与 macOS Objective-C）、过时 Apple 工具产生的二进制 blob、无测试套件；重写用 Rust 产生更可靠可维护的程序（内存安全、类型系统与标准库使跨平台开发更健壮）。
- 崩溃报告是边缘情况：独立程序、必须尽量少用 Firefox 代码库（理想零，不依赖可能有 bug 导致报告器自身崩溃的代码）；必须有 GUI 但不能用 Firefox 跨平台渲染；不用第三方跨平台 GUI crate 的原因：最小化外部代码（简单可审计）、Firefox 树内 vendor 依赖（大依赖难引入）、只有少数 crate 提供原生 OS 观感。
- 构建 GUI 视图抽象：极简平台特定代码——UI 实现提供两个方法：run_loop（运行 UI 循环显示所有窗口直到终止）与 invoke（在 UI 循环线程异步调用函数）；4 个实现：Win32、Cocoa（AppKit/Foundation）、GTK+ 3（BSD 等也用它）、测试实现（虚拟 UI 钩子）。显式非目标：不创建单独 Rust GUI crate，只建覆盖所需用例的足够抽象；容忍少量特殊情形（如 Button 含 Label）。
- UI 模型：主要概念来自 GTK 的声明式结构；顶层 Application（窗口集 + 是否 RTL 区域设置，从 Firefox 资源检查区域设置）；每 Window 含单一根元素；只需 8 种 GUI 元素；Rust 无继承，用 Element { style, element_type } 结构 + ElementType 枚举；ElementBuilder<T> 提供带断言的便捷 setter；ui! 宏提供声明式语法（元素类型 + 方法调用式语法 + 可选子元素花括号）；无自动格式化支持。
- 数据绑定：支持触发事件、同步值（镜像并通知所有克隆变化）、按需值（可查询当前值，用于文本框内容避免每 UI 实现防抖）；Property<T> 类型可设为静态值、同步值或按需值，builder 方法接受 impl Into<Property<T>>；全部 Clone 用 Rc/RefCell（无需线程安全）；先前迭代有生命周期参数需不安全 transmute 生命周期，改为全部 Clone 存静态生命周期回调更可维护。
- 线程与线程安全：UI 实现只在主线程交互（含更新数据绑定）；业务逻辑默认离主线程避免 UI 冻结；把业务逻辑放一个非 Clone 非 Sync 类型（Logic）、UI 与 UI 状态放另一类型（UI），Logic 移到单独线程；通信经入队函数（Box<dyn FnOnce(&T) + Send>）——UI 线程就是 invoke 方法，Logic 线程跑循环经 mpsc::channel 取函数在拥有的值上运行；先前用线程本地存储与中心类型的更复杂方案被简化。
- 本地化：用 fluent（Mozilla 现代工具），本地化体验统一可预测；从 Firefox 安装提取本地化文件，最坏情况 en-US 定义直接捆绑进报告器二进制。
- UI 实现细节：Linux/GTK 最直接（bindgen 生成绑定、模型镜像 GTK 概念、trait 附加拥有数据到 GObject、宏设 GTK 信号与数据绑定胶水）；Windows/Win32 最难（API 无布局原语手动实现布局、大量额外调用得到像样 GUI——窗口颜色、字体平滑、高 DPI、默认字体竟是可怕位图字体需手动取系统默认）；macOS/Cocoa 有棘手部分（无 XCode 不免费获得 Cmd-C 等快捷键需手动实现应用主菜单、处理 autorelease pool、模态窗口嵌套事件循环默认 NSRunLoop 模式不调用排队函数）；测试 UI 用字符串标识符访问元素模拟按钮按压、字段输入。
- 模拟与测试：可模拟崩溃报告器（测试时总模拟）——不仅模拟输入（环境变量、命令行参数）还模拟所有有副作用 std 函数；用 crate 内 std 模块 + crate::std 引用，启用模拟时用自写函数替代（文件系统、环境、启动外部命令）；只模拟现有函数的最小量，若用新 std 函数模拟启用时编译失败防止遗漏副作用；mock 数据经线程本地存储注入（动态作用域形式），mock::builder().set(...).run(...)。
- 测试：可自动测试任意 UI 交互如何影响报告器自身 UI 状态与环境（检查调用哪些程序、网络连接、失败/成功/超时结果）；设 mock 文件系统并在多种场景断言精确文件系统状态；"最后一英里"（每 UI 实现忠实呈现 UI 模型）手动用 mock GUI 测试。
- 成品：外观与此前完全相同（以免用户察觉变化）；新崩溃报告器解除功能请求阻塞：检测安装损坏告知重新安装、检查崩溃系统故障内存硬件、首次提交崩溃用 Firefox 网络栈（尊重代理等用户网络设置）。

## 正文

以下是文章全文翻译。

Firefox 的崩溃报告器但愿多数用户不常经历。但它仍是 Firefox 非常重要的组件，因为它是洞悉最显眼 bug（崩溃主进程的那些）的关键。这些 bug 提供最糟用户体验（整个应用必须关闭），因此修复它们是最高优先级。其他类型崩溃（如内容/标签页崩溃）可由浏览器处理并优雅报告，有时用户甚至不知道出现问题。但主浏览器进程停止时，我们需要另一个独立应用收集崩溃信息并与用户交互。本文详述我们重写崩溃报告器为 Rust 的方法。讨论重写背后的理由、什么使崩溃报告器独特、所用架构与一些实现细节。

**为什么重写？** 虽然恰当处理主进程崩溃很重要，崩溃报告器已有一段时间未获重要开发（除确保崩溃报告与遥测持续可靠交付的开发外）！它长期困于"够好"与"维护可怕"的局部最大：它有 3 个独立 GUI 实现（Windows、Linux 的 GTK+、macOS）、抽象少数东西的胶水代码（多为 C++、macOS 为 Objective-C）、过时 Apple 开发工具产生的二进制 blob、且无测试套件。因此有一堆未行动的功能与改进积压。我们近期多次成功推动降低崩溃率（包括大跃进与许多小 bug 修复），期间崩溃报告器足够满足需求。但我们到达拐点：改进崩溃报告器将提供宝贵洞见以进一步降低崩溃率。因前述原因改进当前代码库困难易错，我们认为适合重写应用，以便更轻松处理功能积压并改善崩溃报告。与 Firefox 许多组件一样，我们决定重写用 Rust，产生更可靠可维护的程序。除常被赞誉的内置内存安全，其类型系统与标准库让推理代码、处理错误与开发跨平台应用远更健壮全面。

**崩溃报告是边缘情况。** 崩溃报告器有许多独特功能，尤其相对其他已移植到 Rust 的组件。其一，它是独立单程序；Firefox 基本没有其他组件这样使用。Firefox 本身启动许多进程作为沙箱化与崩溃隔离手段，但这些进程彼此通信并访问相同代码库。崩溃报告器有非常独特的要求：它必须尽量少用 Firefox 代码库，理想为零！我们不想它依赖可能有 bug 并导致报告器自身崩溃的代码。使用完全独立实现确保主进程崩溃发生时，崩溃原因不会同时影响报告器功能。崩溃报告器也必然有 GUI。这本身可能不把它与其他 Firefox 组件分开，但我们不能利用 Firefox 提供的跨平台渲染优势！所以也需独立实现跨平台 GUI。你可能想可用现成跨平台 GUI crate，但我们有几个理由不这样做：(1) 最小化外部代码：为改善崩溃报告器可靠性（至关重要），我们希望它尽可能简单可审计；(2) Firefox 树内 vendor 所有依赖，因此犹豫引入大依赖（GUI 库可能相当大）；(3) 只有少数第三方 crate 提供原生 OS 观感（或真用原生 GUI API）：崩溃报告器有原生感很重要，既对用户熟悉也利用无障碍功能。所以第三方跨平台 GUI 库不是有利选项。这些要求大幅收窄可用方法。

**构建 GUI 视图抽象。** 为让崩溃报告器更可维护（且未来易加新功能），我们希望平台特定代码尽可能少而通用。可用简单 UI 模型实现，转换为每平台原生 GUI 代码。每个 UI 实现需提供两个方法（基于任意平台特定 &self 数据）：run_loop（取 Application 模型运行应用，阻塞直到完成）与 invoke（在 UI 循环线程异步调用函数）。目标平台一般有相似线程假设：UI 单线程运行、通常运行阻塞于新事件直到收到结束信号的事件循环。有些情况需在 UI 线程异步运行函数（显示窗口、更新文本字段等），invoke 方法定义如何做。此线程模型使平台 GUI 框架易用：程序期间一切调用原生函数都发生在单线程（实际是主线程）。有 4 个 UI 实现：Win32 实现、Cocoa（AppKit 与 Foundation 框架）macOS 实现、GTK+ 3 Linux 实现（Linux 不提供自带 GUI 原语，Firefox Linux 已随 GTK 提供现代感 GUI，报告器也能用；Mozilla 不直接支持的平台如 BSD 也用 GTK 实现）、以及允许测试钩进虚拟 UI 戳东西的测试实现。最后细节：崩溃报告器（至少现在）GUI 相当简单。因此开发显式非目标是创建单独 Rust GUI crate。我们只想建足够覆盖报告器所需用例的抽象。未来需更多控件可加进抽象，但避免花多余精力填充每个 GUI 用例。同样，我们容忍少量 hack 与内置边缘情况避免不必要开发。例如模型定义 Button 为含任意元素的元素，但 Win32 或 AppKit 真支持需大量定制代码，所以我们对 Button 含 Label（现在只需这个、也是易得原语）做特殊处理。我很高兴地说这种特殊情形真不多，但我们对我们需要的那几个感到舒适。

**UI 模型。** 我们的模型是对主要存在于 GTK 概念的一种声明式结构化。GTK 是成熟库、有经过验证的高层 UI 概念，适合我们的抽象且使 GTK 实现相当简单。例如 GTK 做布局的最简单方式（容器 GUI 元素加每元素边距/对齐）对我们 GUI 足够，所以模型用类似定义。值得注意的是，这个"简单"布局定义实际相当高层，使 macOS 与 Windows 实现复杂一点（但此权衡值得创建 UI 模型的轻松）。UI 模型顶层类型是 Application，定义为顶层 Window 集（虽然我们应用只有一个）与当前区域设置是否从右到左。我们检查 Firefox 资源使用 Firefox 会用的同一区域设置，不依赖原生 GUI 区域设置。每个 Window 含单一根元素。模型其余由少数典型容器与原始 GUI 元素组成。崩溃报告器只需 8 种 GUI 元素！而且 Progress 现在真用作 spinner 而非指示真实进度，所以并非严格必需（但展示很好）。Rust 不显式支持面向对象继承概念，你可能好奇每个 GUI 元素如何"扩展"Element。图中关系有些抽象；实现的 Element 是：`pub struct Element { pub style: ElementStyle, pub element_type: ElementType }`，ElementStyle 含元素公共属性（对齐、大小、边距、可见性与启用状态），ElementType 是含每个特定 GUI 元素作为变体的枚举。

**构建模型。** 模型元素都供 UI 实现消费，因此几乎所有字段公开可见。作为构建元素的独立接口，我们定义 ElementBuilder<T> 类型，方法保持断言并提供便捷 setter。例如许多方法接受 impl Into<MemberType> 参数，margin() 等方法设多个值（也可 margin_top() 更具体）。有通用 impl<T> ElementBuilder<T> 为各 ElementStyle 属性提供 setter，然后每特定元素类型也可提供自己的 impl ElementBuilder<SpecificElement> 带元素类型独有附加属性。我们把 ElementBuilder<T> 与最后一块拼图组合：ui! 宏。此宏让我们以声明式方式写 UI，例如构建"崩溃详情"窗口（Window 标题、可见性绑定、模态、大小、对齐，内含 VBox > Scroll > TextBox 与带 on_click 回调的 Button > Label）。ui! 实现相当简单：第一个标识符提供元素类型并创建 ElementBuilder<T>；其后剩余方法调用式语法在（可变的）builder 上调用。可选地，最终花括号集表示元素有子元素，此时宏递归调用创建它们并对 builder 调 add_child（只需确保 builder 有 add_child 方法）。最终语法转换相当简单，但我相信此宏不只是语法糖：它让阅读编辑 UI 清晰不少，因为元素层级表示在语法中。不幸的是无法支持此类宏 DSL 的自动格式化，开发者需保持合理格式。

**数据绑定。** 有几个类型声明动态（运行时可变）值。UI 需要支持不同行为：触发事件（按钮点击时发生什么）、同步值（镜像并通知所有克隆变化）、按需值（可查询当前值）。按需值用于获取文本框内容而非同步值，努力避免在每 UI 实现防抖。作为便利我们创建涵盖值导向字段的 Property 类型。Property<T> 可设为静态值（T）、同步值（Synchronized<T>）或按需值（OnDemand<T>）。它支持每个的 impl From，使 builder 方法可写成 fn my_method(&mut self, value: impl Into<Property<T>>)，允许任何受支持值传入 UI 声明。实现细节不多说（如你所料），但值得注意这些都 Clone 以轻松共享数据绑定：用 Rc（无需线程安全）与按需访问回调的 RefCell。上节示例中 show_details 是 Synchronized<bool> 值。变化时 UI 实现改变关联窗口可见性。Button on_click 回调把同步值设为 false 隐藏窗口（注意此示例详情窗口从不关闭，只显示隐藏）。先前迭代中数据绑定类型有生命周期参数指定事件回调有效生命周期。虽然我们能使其工作，它极大复杂化代码，尤其无法向编译器传达生命周期正确协变性，因此有额外不安全代码 transmute 生命周期（虽包含为实现细节）。这些生命周期还有传染性，要求部分复杂语义传播进存储 Property 字段的模型类型。其中许多是为避免克隆值进回调，但把类型改为全部 Clone 并存储静态生命周期回调值得让代码远更可维护。

**线程与线程安全。** 细心的读者会记得我们讨论的线程模型涉及只在主线程与 UI 实现交互——包括更新数据绑定，因为 UI 实现可能在其上注册回调！虽然我们可把所有东西放主线程，但尽量多离 UI 线程做通常是更好体验，即使我们没做多少阻塞（虽然提交崩溃报告时会阻塞）。我们希望业务逻辑默认离主线程，使 UI 永不冻结。可用仔细设计保证。最简单方式是把全部业务逻辑放一个（非 Clone、非 Sync）类型（叫 Logic），在另一类型（叫 UI）构造 UI 与 UI 状态（如 Property 值）。然后把 Logic 值移进单独线程，保证 UI 不能直接与 Logic 交互、反之亦然。当然我们有时确实需要通信！但想确保通信总委托给拥有值的线程（而非值直接交互）。可创建每个类型的入队函数存储于相反类型实现。此类函数接收要在拥有线程运行的装箱函数（Box<dyn FnOnce(&T) + Send + 'static>）。创建简单：UI 线程就是之前简述的 UI 实现 invoke 方法；Logic 线程只跑循环取这些函数在拥有的值上运行（用 mpsc::channel 入队传递）。现在每类型可异步调用对方方法，保证在正确线程运行。先前迭代用更复杂方案（线程本地存储与负责创建线程与委托函数的中心类型）。但如此基础的两线程互相委托用例，我们能蒸馏到所需本质，大幅简化代码。

**本地化。** 此重写的一个好收益是能把崩溃报告器本地化提升到现代工具水平。Firefox 几乎其他所有部分都用 fluent 处理本地化。崩溃报告器用 fluent 使本地化者体验更统一可预测；他们无需理解超过一种本地化系统（崩溃报告器是旧系统最后坚持者之一）。在新代码中极易使用，只需一点额外代码在崩溃报告器运行时从 Firefox 安装提取本地化文件。最坏情况找不到或无法访问这些文件时，en-US 定义直接捆绑进崩溃报告器二进制。

**UI 实现。** 不深入细节，但值得各谈一点。**Linux（GTK）**：GTK 实现大概最直接简洁。用 bindgen 生成所需 GTK 函数的 Rust 绑定（避免 vendor 任何外部 crate）。然后简单调用对应 GTK 函数按模型描述设置 GTK widget（记住模型镜像了 GTK 概念）。GTK 相当现代、为人（而非某些平台自动化工具）编写，因此没有真需要处理的痛点或异常行为。我们有一组 trait 轻松把拥有数据附加到 GObject（确保数据有效、GObject 销毁时正确 drop），几个宏设置 GTK 信号与数据绑定类型间胶水代码。**Windows（Win32）**：Windows 实现可能是最难写的，因为 Win32 GUI 现在极少有人写、API 显其年代。我们用 windows-sys crate 访问 API 绑定（已因许多其他 Windows API 用途 vendor 在代码库）。此 crate 由微软直接从 Windows 函数元数据生成，绑定与 bindgen 可能产生的不太不同（虽然可能更准确）。要克服许多障碍。其一，Win32 API 不提供任何布局原语，因此我们使用的高层布局概念（允许优雅调整大小/重定位）须手动实现。还有相当多额外 API 调用只为得到稍微像样的 GUI（正确窗口颜色、字体平滑、高 DPI 处理等）。甚至默认字体也是可怕位图字体而非更现代系统默认；需手动检索系统默认并设为字体，有点意外！我们有一组 trait 帮助创建自定义窗口类与管理类实例的关联窗口数据，还有包装类型恰当管理句柄生命周期与类型转换（主要是 String 与空终止宽字符串互转）作为 API 上额外安全层。**macOS（Cocoa/AppKit）**：macOS 实现有棘手部分，因为绝大多数 macOS GUI 用 XCode 编写、有大量自动与生成部分（如 nib）。我们再次用 bindgen 生成 Rust 绑定，这次为 macOS 框架头中的 Objective-C API。与 Windows 和 GTK 不同，不用 XCode（其在新项目模板中生成）创建 GUI 时不会免费获得 Cmd-C、Cmd-Q 等键盘快捷键。为拥有用户期望的典型快捷键，需手动实现应用主菜单（它管理键盘快捷键）。还需处理运行时设置：创建 Objective-C autorelease pool、把窗口与应用（独立概念）带到前台等。甚至实现 invoke 调用主线程函数也有细微差别，因为模态窗口用嵌套事件循环，默认 NSRunLoop 模式不会调用排队函数。我们写了一些简单辅助类型与宏，轻松从 Rust 代码实现、注册与创建 Objective-C 类。用于创建委托类与子类化一些控件（如 NSButton），轻松安全管理类底层 Rust 值内存并正确注册类方法 selector。**测试 UI**：很简单，不创建 GUI，允许直接与模型交互。ui! 宏在测试启用时支持额外语法为每元素可选设置字符串标识符。单测中用这些字符串访问与交互 UI。数据绑定类型测试中也支持额外方法轻松操纵值。此 UI 允许模拟按钮按压、字段输入等，确保其他 UI 状态按预期变化并模拟系统副作用。

**模拟与测试。** 重写的重要目标是给崩溃报告器加测试；旧代码严重缺测试（部分因 GUI 单测以难著称）。**模拟一切**：新代码中我们无论是否运行测试都可模拟崩溃报告器（虽然测试时总模拟）。这很重要，因为模拟允许我们（手动）在各种状态运行 GUI 检查 UI 实现正确且渲染良好。我们的模拟不仅模拟崩溃报告器输入（环境变量、命令行参数等），还模拟所有有副作用的 std 函数。通过 crate 内 std 模块实现，其余代码用 crate::std。禁用模拟时 crate::std 即 ::std。启用时用我们编写的一组函数替代：模拟文件系统、环境、启动外部命令与其他副作用。重要的是只实现模拟现有函数的最小量，这样若使用 std::fs、std::net 等新函数，crate 在启用模拟时编译失败（使我们不漏掉副作用）。这听起来工作量大，但你可能惊讶 std 真需模拟的很少，且多数实现相当直接。现在代码用不同模拟函数，需要注入期望 mock 数据的方式（测试与正常模拟操作）。例如我们能返回 File 读取的一些数据，但需能为测试设置不同数据。不深入细节，我们用线程本地 mock 数据存储实现。这样无需改代码容纳 mock 数据；只需在设置与检索处改。编程爱好者会认出这是动态作用域形式。实现允许 mock 数据用 mock::builder().set(crate::std::env::MockCurrentExe, "work_dir/crashreporter".into()).run(|| crash_reporter_main()) 设置（测试中），crate::std::env 实现中 current_exe() 用 MockCurrentExe.get(|r| r.clone()) 检索。

**测试。** 有了模拟设置与测试 UI，我们能广泛测试崩溃报告器行为。"最后一英里"（每 UI 实现忠实呈现 UI 模型）不易自动化；我们对每平台用 mock GUI 手动测试。除此之外，我们可自动测试任意 UI 交互如何让崩溃报告器影响自身 UI 状态与环境（检查调用哪些程序、建立哪些网络连接、失败/成功/超时时发生什么）。还设置 mock 文件系统并在多种场景断言崩溃报告器完成后的精确文件系统状态。这大幅增强对当前行为的信心并确保未来变更不改动它们，对崩溃报告管道如此基本组件至关重要。

**成品。** 当然我们不能写完这些不展示崩溃报告器图片！这是 Linux 用 GTK 的样子。其他 GUI 实现看起来相同但以原生观感样式化。注意目前我们想让它看起来与此前完全相同。所以如果你不幸看到它，不应显得有任何变化！有了新的清理过的崩溃报告器，我们终于能解除一系列功能请求与 bug 报告：检测安装是否损坏并告知用户重装 Firefox；检查崩溃系统是否有故障内存硬件；首次提交崩溃用 Firefox 网络栈（尊重代理等用户网络设置）。我们期待迭代进一步改善崩溃报告器功能。但归根结底，你永远看不到或不用它才是最好，我们一直朝此目标努力！
