# 幕后：用 Claude Mythos Preview 加固 Firefox

## 摘要

- 两周前 Mozilla 宣布在 Claude Mythos Preview 等 AI 模型帮助下识别并修复了 Firefox 中数量空前的潜在安全 bug；本文详述工作方法、发现与对其他项目的建议。
- 几个月前 AI 生成的安全 bug 报告还主要是"垃圾"（看似正确实则错误的报告给维护者带来不对称成本）；两个因素改变格局：模型能力大幅提升，以及 Mozilla 大幅改进驾驭模型的技术（引导、扩展与堆叠以生成大量信号并滤除噪声）。
- 展示了 12 个修复背后的报告样本（跨越多个浏览器子系统）：JIT 错误相等性检查创建假对象原语（2024918）；15 年历史的 <legend> 元素 bug（2024437）；IPC 竞态触发 IndexedDB UAF 与沙箱逃逸（2021894）；跨 IPC 边界的原始 NaN 伪装成标签化 JS 对象指针（2022034）；嵌套事件循环触发的 <object> 属性 setter UAF（2024653）；WebTransport 证书洪泛触发父进程 UAF（2022733）；模拟恶意 DNS 服务器触发缓冲区过度读取与栈内存泄露（2023958）；20 年历史 XSLT 重入 key() bug（2025977）；颜色选择器嵌套事件循环 UAF（2027298）；父进程壁纸解码信任推理（2023817）；RLBox 沙箱逃逸（2029813）；rowspan=0 语义溢出 16 位布局位域（2026305）。
- 若干是沙箱逃逸，须与其他利用组合才能完整攻陷 Firefox；模型被允许修补 Firefox 源码（限沙箱进程运行），此类 bug 以模糊测试著称地难找。
- 模型没找到什么同样有趣：无法绕过 Firefox 分层防御，例如冻结原型（prototype pollution 逃逸路线被架构变更阻断）。
- 管道构建：早期 LLM 代码审计假阳性率过高；智能体框架能创建并运行可复现测试用例后完全改变局面；Mozilla 在自身模糊测试基础设施上构建框架，先用 Claude Opus 4.6 小规模实验找沙箱逃逸，再跨多个临时 VM 并行化，每个 VM 针对特定目标文件猎取 bug 并写回 bucket；发现子系统必要但不充分，需与完整安全 bug 生命周期（去重、跟踪、分流、修复交付）集成；管道本质项目特定，需与处理 incoming bug 的工程师紧密反馈迭代。
- 模型升级：管道就绪后换模型平凡；升级让系统同时在发现潜在 bug、创建 PoC 测试用例与阐述病理影响上变好。除修复 Claude Mythos Preview 识别的 271 个 bug（Firefox 150）外，还在 149.0.2、150.0.1、150.0.2 交付更多修复；100+ 人贡献代码。
- 要点：任何构建软件的人现在都能用框架+现代模型找 bug 加固代码；从简单提示开始观察迭代；扫描目前聚焦特定代码区域，近期计划集成到 CI 扫描落地补丁。
- FAQ：内部报告的 bug 分组为"rollup"CVE——Firefox 150 有三个内部 rollup：CVE-2026-6784（154 bugs）、CVE-2026-6785（55）、CVE-2026-6786（107），合计 316 超过宣布的 271（其余来自其他模型、模糊测试等）；4 月共修复 423 个安全 bug（41 外部报告，111 内部发现中约三分之一各来自 Claude Mythos 管道其他版本、其他模型管道、模糊测试等技术）；另直接给 Anthropic 记 3 个 CVE。安全评级：sec-critical/sec-high（正常用户行为可触发，如浏览网页）、sec-moderate（本应 sec-high 但需受害者异常复杂步骤）、sec-low（烦人但远不造成伤害）；271 个 bug 中 180 sec-high、80 sec-moderate、11 sec-low。sec-high 不等于实际可利用：Firefox 有纵深防御架构，单 bug 通常不足以攻陷；Mozilla 一般不做利用构建，基于可预测崩溃症状（如 AddressSanitizer 报告的 UAF/OOB）分类 sec-high。

## 正文

以下是文章全文翻译。

两周前我们宣布在 Claude Mythos Preview 与其他 AI 模型帮助下识别并修复了 Firefox 中数量空前的潜在安全 bug。这篇文章我们将更详细地介绍如何开展这项工作、发现了什么，以及为其他项目利用新兴能力加固自身提供建议。

**突然，bug 变得很好。** 就在几个月前，AI 生成的开源项目安全 bug 报告大多以"不受欢迎的垃圾"著称。处理看起来合理但错误的报告给项目维护者带来不对称成本：提示 LLM 找代码中的"问题"廉价且容易，回应它却缓慢昂贵。很难夸大这短短几个月这一动态对我们改变有多大。这源于两个主要因素组合：模型能力大幅提升；我们大幅改进驾驭这些模型的技术——引导、扩展与堆叠它们以生成大量信号并滤除噪声。通常我们在修复交付与安全公告发布后把详细 bug 报告保密几个月，主要为保护因种种原因更新缓慢的用户。鉴于该主题非凡关注度与整个软件生态行动的紧迫性，我们做出审慎决定，揭开最近交付修复背后的一小部分报告样本。我们尝试从各浏览器子系统取材，但选择过程仍有点随意。尽管如此，我们希望这些报告的深度与多样性为我们的能力评估及对防御者开始应用这些技术的呼吁提供可信度。以下为 12 个报告概要（含 bug ID 与描述）：(2024918) 错误相等性检查可使 JIT 优化掉活跃 WebAssembly GC 结构的初始化，创建带潜在任意读/写的假对象原语——代码经内外部研究者大量模糊测试；(2024437) <legend> 元素中一个 15 年历史 bug，由浏览器遥远部分边缘情况的细致编排触发，包括递归栈深度限制、expando 属性与循环收集；(2021894) 可靠利用 IPC 竞态，让被攻破内容进程操纵父进程 IndexedDB 引用计数触发 UAF 与潜在沙箱逃逸；(2022034) 原始 NaN 跨 IPC 边界可伪装成标签化 JS 对象指针，把 double 反序列化变成父进程假对象原语用于沙箱逃逸；(2024653) 编织嵌套事件循环、pagehide 监听器与垃圾收集的复杂测试用例，触发 <object> 元素属性 setter 中 UAF；(2022733) 用数千证书哈希洪泛 WebTransport 拉伸引用计数重复制循环中的竞态触发父进程 UAF，并经 IPC 从被攻破内容进程利用该竞态；(2023958) 通过拦截 glibc DNS 函数调用模拟恶意 DNS 服务器复现 UDP→TCP 回退边缘情况，在 HTTPS RR 与 ECH 解析期间触发缓冲区过度读取与父进程栈内存泄露；(2025977) 20 年历史 XSLT bug：重入 key() 调用导致哈希表重哈希，在原始条目指针仍在使用时释放后备存储（我们修复的多个涉及 XSLT 的 sec-high 问题之一）；(2027298) 修补颜色选择器模拟否则不可自动化的用户选择，然后用同步输入事件旋转嵌套事件循环，重入 actor teardown 并在回调展开时释放它，触发内容进程 UAF；(2023817) 被攻破内容进程可发送任意壁纸图像在父进程解码，可与图像解码器假设性漏洞配对逃逸沙箱——需要难以自动化的父进程输入信任级推理；(2029813) 利用沙箱边界未受信侧向受信侧复制值的验证逻辑缺口，逃逸第三方库进程内沙箱技术 RLBox；(2026305) 极小测试用例利用 HTML 表格特殊 rowspan=0 语义，追加 >65535 行绕过钳制溢出 16 位布局位域，模糊测试多年未发现。

注意其中若干是沙箱逃逸，需与其他利用组合才能完整攻陷 Firefox。这些报告假设渲染站点内容的沙箱进程已被某个单独 bug 攻破，正运行攻击者控制的机器码试图升级控制进入特权父进程。构造沙箱逃逸时，模型被允许修补 Firefox 源码，只要修改代码限制仅在沙箱进程运行。此类 bug 以模糊测试著称地难找，虽然我们在开发新技术缩小差距上有些成功，AI 分析对该关键表面提供更全面覆盖。与模型发现的一样有趣的是它们没发现什么——不是因为没尝试，而是无法绕过 Firefox 分层防御。例如，近年我们收到几份聪明报告，通过在特权父进程触发原型污染逃逸进程沙箱。我们没有逐个修复，而是做了架构变更默认冻结这些原型。审计框架日志时，我们看到许多追求此逃逸路线的尝试被该设计挫败。观察先前加固工作的直接回报甚至比发现修复更多 bug 更令人满足。

**驾驭模型构建加固管道。** 过去几年我们在内部实验 LLM 代码审计，早期尝试用 GPT 4 或 Sonnet 3.5 静态分析高风险代码找漏洞。实验有前景，但高假阳性率使扩展不切实际。能可靠检测安全问题的智能体框架的引入彻底改变这一点。它们能找真 bug 并驳回不可复现的猜测。此类框架关键特性是：给定正确接口与指令，能创建并运行可复现测试用例动态检验代码 bug 假设。修复 2 月 Anthropic 送来的初始问题集后，我们在现有模糊测试基础设施上构建自己的框架。我们从小规模实验开始，用 Claude Opus 4.6 提示框架找沙箱逃逸。即使这个模型，我们也识别出可观数量的未知漏洞，需要对多进程浏览器引擎代码复杂推理。起初我们在终端监督过程实时观察并调优提示与逻辑。运行良好后，跨多个临时 VM 并行化作业，每个 VM 负责在特定目标文件内猎取 bug 并把发现写回 bucket。发现子系统必要但不充分。为扩展努力，需与完整安全 bug 生命周期集成：决定找什么、在哪找、如何处理产出——包括对已知问题去重、跟踪 bug、分流与交付修复。虽然模型是驱动框架的核心原语，完整管道对规模化有用是必需的。虽然框架可跨项目复用，管道本质上项目特定，反映每个代码库的语义、工具与流程。搭建它需要大量迭代，与处理 incoming bug 的 Firefox 工程师紧密反馈循环。

**升级模型。** 端到端管道就位后，新模型可用时替换平凡。早期建立管道帮我们用公开模型找到若干严重 bug，也让我们有机会评估 Claude Mythos Preview 时立即起步。以我们的经验，模型升级提升整个管道效能：系统同时在发现潜在 bug、创建 PoC 测试用例与阐述其病理与影响上变好。除修复 Claude Mythos Preview 在 150 版本识别的 271 个 bug 外，我们还在 149.0.2、150.0.1 与 150.0.2 交付更多修复。我们也继续用其他手段内部找 bug，且与其他项目类似，近几个月外部报告显著增加。最终每个 bug 都需要细心关注才能恰当修复。跟上这空前数量在过去几个月带来大量工作与长日，我们为团队迎接挑战的表现极其自豪。100 多人为此贡献代码交付最安全的 Firefox。除编写评审补丁外，其他人构建扩展管道、分流、测试修复并为每个 bug 管理发布流程。

**要点。** 任何构建软件的人现在都能开始用框架+现代模型找 bug 加固代码。我们建议现在就开始。你会找到 bug，并让自己在新模型可用时立即受益。可从非常简单提示开始，然后观察与迭代。我们初始提示与这里描述的无甚区别。通过迭代我们构建了大量编排与工具优化扩展管道，但内循环本质不变：这部分代码有 bug，请找到它并构建测试用例。我们还没有穷尽 Firefox 所有潜在 bug，但对轨迹相当满意。今天我们的扫描主要聚焦基于人工判断与自动化信号混合指示系统查找的特定代码区域（文件、函数）。近期我们打算把分析集成进持续集成系统，扫描落地树中的补丁。模型对提供上下文形式相当灵活，我们期望基于补丁的扫描与基于文件的扫描一样好甚至更好。当前时刻危险但也充满机遇。让我们携手保护互联网。
