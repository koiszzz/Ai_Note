## 摘要

- 这是 Distilled 更新"在机器人时代保持 Web 开放与私密"的技术配套文；深入问题空间、提议设计与待解问题。
- 问题：私密窗口浏览新闻站点、VPN 购物、加强反指纹防御看视频——都会看到注册墙、拦截页与无尽 CAPTCHA；网站有正当理由阻止机器人（SEO 评论垃圾、凭据填充、DDoS 等容量滥用），但反滥用工具日益双失败：浏览器隐私保护拆解反滥用系统依赖的被动信号，生成式 AI 使 CAPTCHA 失效（机器人比人更快更可靠解）；许多站点转向侵入性机制（要邮箱、联邦登录、禁用 VPN），伤害用户隐私与体验；浏览器 AI 智能体使紧张加剧——站点无法区分代表个人用户的智能体与容量滥用智能体，往往两者都阻止。
- 便利方案的代价：大型生态玩家提出依赖其对主导操作系统控制与消费硬件深度集成的方案（设备证明）：Google 的 Web Environment Integrity（2023 年放弃）证明用户代理本身与 OS 设备，用户会双重失去控制（证明者决定祝福哪些 OS/设备，网站决定接受哪些软件），若站点采用允许列表构建新浏览器几乎不可能；Apple 的 Private Access Tokens（2022 年部署）基于 IETF 标准化的 Privacy Pass 协议，很多做得对（用户收到可呈现给网站而不关联访问的一次性 token 续期批次），但依赖设备证明——呈现 PAT 告诉网站你被锁进 Apple 的可接受软件规则，且技术上无法向其他稀缺源开放而不损害隐私属性——若广泛部署，Web 访问将绑定于向少数难以更换厂商购买昂贵硬件。两种方法最终都敌视用户与 Web 开放性。
- 更好路径：机器人的伤害源于超越人类规模运作能力；站点防容量滥用不需要知道用户身份或密码学证明运行经批准软件——若知道访客受站点设定速率限制就够了。速率限制只有绑定稀缺之物才有意义；硬件只是稀缺的一种选择——任何用户已有而攻击者无法轻易规模化制造的东西都行：邮箱与电话号码天然稀缺、付费订阅与真实用户同价、甚至免费服务账户也需要非平凡工作。可构建开放生态：多方提供稀缺信号，每站点选择接受哪些——避免把控制权转移给设备制造商。具体示例：VPN 提供商充当订阅服务为用户背书，站点可按用户个体限速——用户既能浏览更少摩擦又不用放弃 VPN。
- 关键难点：开放 Web 上维持隐私地构建此系统真的很难——需要把"此用户持有某稀缺之物"的信息从一站点暴露给其他站点作限速基础，而这正是隐私保护浏览器十年来封锁的跨站信息流。目标是最小信息流出：单个比特传达用户是否低于站点速率限制；泄露更多（如稀缺源）不可接受。
- 基础：隐私保护方法的密码学基础已存在——Privacy Pass 协议（2018 年开发减少 Cloudflare CAPTCHA 对 Tor 用户摩擦）：核心原语是发行与赎回间不可链接的 token；已在 Apple（Private Cloud Compute、Private Relay）、Chrome（两跳 IP 保护）、Kagi（私有搜索）成功部署——部分因少量方预先商定谁发行谁接受。
- 应用到开放系统带来真正挑战：(1) 即使 token 不可链接，知道用户可访问特定发行者本身是隐私泄露（推断用户符合相关发行标准；站点集成为指纹）；零知识通用技术可证明"持有可接受发行者集的 token"而不揭示哪个——发行者盲化；定制方法可大幅改善。(2) 站点如何决定信任谁发行 token——发行者行为不端则速率限制失效；但防止站点学习用户可访问哪些发行者时，站点只知道用了受信发行者之一，难以检测错误——需经 Prio 等多方计算（MPC）为每发行者算聚合分数。(3) Privacy Pass 难以动态调整速率限制——发行后 token 难撤销；匿名信用 token（ACT）解决：带内部计数器的凭据，呈现时站点可检查计数器超阈值并变异它，确切值从不泄露防止跟踪。
- 组合：PACT（Private Access Control Tokens）。2026 年 5 月 Mozilla 与 Cloudflare、Chrome 及其他 Web 利益相关者参与 W3C CG 会议开始勾勒设计。Anchors（锚）提供稀缺源（订阅、良好账户、验证电话），按 Privacy Pass 模型发行 Endorsement token 批次；Moderator（调节者）为站点处理速率限制、验证 Endorsement 并发行带状态的 Credential；每站点限提名单一 Moderator（常见情形站点自己扮演）；发行者盲化保证 Moderator 只知 Endorsement 来自其信任的 Anchor 之一。
- 三流程：用户经正常交互从 Anchor 获得 Endorsement（相对罕见操作，稀缺源不应太易积累）；到达使用 Moderator 的站点时浏览器花 Endorsement 换 Credential（隐藏用了哪个 Anchor，Moderator 决定初始余额，无合适 Endorsement 时现有机制如 CAPTCHA/账户创建可引导同样方式——系统退化为今天体验而非锁死用户）；浏览时浏览器呈现 Credential，Moderator 更新内部状态（奖励良性、惩罚可疑，但无法跟踪使用或跨站点识别；撤销同机制——拒绝返回更新 Credential）。
- 隐私保持接近单比特：密码学不可链接性确保连续呈现无法关联成历史；每站点绑定单一 Moderator 防止 Moderator 集变跨站指纹；Anchor 到 Credential 交换在隔离浏览上下文进行。发行者盲化的额外隐私使 Moderator 参与更难（不能给强 Anchor 的 Credential 比弱 Anchor 更多访问，否则泄露——初始访问须跨池统一，按最弱设定），但可按持有者行为更新凭据随时间积累访问。开放生态还需站点能有效决策信任哪些 Anchor——Prio 等 MPC 系统在用户呈现 Credential 时提供识别所用 Anchor 的加密份额、私密聚合计算发行者质量。
- 下一步：架构形状正确但细节待解决、需严格隐私安全分析；在开放中做：IETF 适合底层密码协议、W3C 适合上层 WebAPI；草稿规范准备好即提交；欢迎生态协作：浏览器厂商、站点运营者、反滥用提供商与密码社区。若成功，可提供让 Web 保持开放私密、同时给站点所需限速信号。

## 正文

以下是文章全文翻译。

这是我们对 Distilled"在机器人时代保持 Web 开放与私密"更新的技术配套文。这里我们更深入看问题空间、提议的设计与仍需解决的问题。

**机器人（与隐私保护浏览器）不受欢迎。** 在私密窗口浏览新闻站点。用 VPN 在大型零售商购物。用加强反指纹防御访问视频流平台。你会看到同样回应：注册墙、拦截页与无尽 CAPTCHA。信息明确：如果我们认为你可能是机器人，你不受欢迎。网站有阻止机器人的正当理由。机器人使容量滥用成为可能——如果必须由人执行就不会可行的滥用。例如：SEO 评论垃圾、凭据填充与 DDoS 攻击。因此许多站点采用专用反滥用工具，旨在阻止机器人同时最小化人类访客摩擦。不幸的是，该工具日益在两个任务上都失败。浏览器隐私保护正在拆解反滥用系统依赖以识别区分访客的被动信号。同时生成式 AI 的进步使 CAPTCHA 失效：机器人现在比人类更快更可靠地解决它们。许多站点转向更侵入性机制，现在要求访客披露识别信息，如邮箱地址、联邦登录或禁用 VPN。这对用户意味着更大摩擦（首次访问提供这些细节耗时），也损害隐私（这些细节实现浏览器隐私保护本意缓解的同类跨站追踪）。用户因此陷入两难：越有效保护隐私，网站越难区分他们与机器人，待遇越差。网站运营者也受苦：他们强加于良行访客的额外摩擦伤害站点，但许多人愿意付代价如果它能缓解容量滥用。基于浏览器的 AI 智能体使紧张更尖锐。站点可能想允许代表个体用户的智能体，同时阻止容量滥用智能体。但无有效机制区分两者，网站选择两者都阻止。这伤害用户（应自由选择访问 Web 的用户代理）、伤害难以互操作的新浏览器与智能体、伤害失去合法访客的站点。结果是 Web 对所有人变糟。用户得到更多摩擦或更少隐私或两者。网站运营者看到更多容量滥用，且他们添加的摩擦赶走本会消费内容或服务的用户。新用户代理难以像常规浏览器访问相同内容。

**便利方案的代价。** 一些大型生态玩家提出利用其对主导操作系统控制与消费硬件深度集成的方案。这些依赖设备证明：硬件级烤入设备的标识符与特权代码，让制造商证明用户设备上运行什么软件。向 Web 暴露此功能意味着向站点证明用户运行经批准软件、硬件可信，因此不是机器人。有两个实质提案。Google 的 Web Environment Integrity（2023 年放弃）是生硬版本。它证明用户代理本身以及所用操作系统与设备。用户会以两种方式失去控制：一次对证明者（决定哪些 OS 与设备可被祝福），再次对网站（决定接受哪些软件）。若站点采用批准用户代理允许列表，构建新浏览器将几乎不可能，站点可从任何其选择的用户代理撤回访问。Apple 的 Private Access Tokens（2022 年部署其生态）有更微妙的问题。构建于 IETF 标准化的 Privacy Pass 协议，它们很多做对了：用户收到可呈现给网站而不链接其访问的续期一次性 token 批次。这为用户提供隐私，并展示速率限制是站点有效工具——两点我们稍后回到。然而 Private Access Tokens 依赖设备证明，要求硬件制造商全面控制用户设备。呈现 PAT 告诉网站你被锁进 Apple 的可接受软件规则。由于 PAT 的技术设计，无法在不损害系统隐私属性的情况下向其他稀缺源开放系统，意味着若更广泛部署，Web 访问将绑定于从少数难以更换厂商购买昂贵硬件。两种方法最终都敌视用户与 Web 开放性。两者都基于用户设备中处于制造商控制、超越用户自身的部分。若广泛部署，Web 将变成又一个围墙花园，集中看门人控制可接受的硬件、操作系统与软件。这些方案对已主导生态的玩家有多方便，我们都认为有更好路径。

**更好的前进路径。** 机器人的伤害源于其超越人类规模运作的能力。站点防容量滥用其实不需要知道用户身份或收到其运行经批准软件的密码学证明。若站点知道其访客受站点设定的速率限制约束，那就够了。速率限制只有绑定稀缺之物才有意义——攻击者无法廉价复制以逃避限制的东西。不锚定于稀缺资源（如 Private Access Tokens 中的可信硬件），攻击者可生成所需任意多新鲜身份绕过速率限制。然而硬件只是稀缺的一种选择。任何用户已有而攻击者无法轻易规模化制造的东西都行：邮箱地址与电话号码天然稀缺。付费订阅花攻击者与真实用户相同成本。即使在免费服务维护账户也需要非平凡工作。如果我们能在 Web 上使用这些稀缺信号会怎样？我们可以构建开放生态，多方提供稀缺信号，每站点选择接受哪些。通过开放谁可提供信号、让站点选择接受哪些，我们可避免把控制权转移给设备制造商及由此产生的伤害。作为谁适合提供此类信号的具体示例，考虑 VPN 提供商充当订阅服务。站点常不分青红皂白阻止 VPN 用户，无论是刻意政策选择还是按 IP 地址限速访客的间接后果。但 VPN 订阅是稀缺性的完美来源。若 VPN 提供商能为用户背书、站点可单独按用户限速——那么用户就能以更少摩擦浏览 Web 而不放弃 VPN 使用。关键在于在开放 Web 上维持用户隐私地构建能实现此的系统真的很难。它要求我们从一站点取信息（此用户持有某稀缺之物）并暴露给其他站点，使其作为限速基础。让一个站点验证来自另一站点的信号，正是隐私保护浏览器过去十年封锁以防跨站追踪的信息流类型。我们的目标是不超过最小信息通过：单个比特传达用户是否低于站点设定的速率限制。泄露更多——如限速锚定的稀缺源——不可接受。启用新跨站信息流可能感觉像以更好访问换取隐私妥协，但现实更微妙。若新系统让站点远离要求访客可识别（无论经指纹还是登录表单），它可以是隐私与访问的双赢。

**基础。** 好消息是隐私保护方法的密码学基础已存在。Privacy Pass 协议（2018 年开发以减少 Cloudflare CAPTCHA 对 Tor 用户的摩擦）引入核心原语：发行与赎回间不可链接的 token。你向发行者证明某事（如解 CAPTCHA）、收到一些 token、稍后向网站呈现 token。网站可验证 token 合法，但无法链接到发行给它的用户。Privacy Pass 继续在发行者与验证者有预先信任关系的系统中成功部署：Apple 用它认证 Private Cloud Compute 与 Private Relay 用户而不把活动链接到身份，Chrome 用于两跳 IP 保护，Kagi 提供私有搜索。这些部署部分因少量方预先商定谁发行 token 谁接受。把此方法应用到任何站点可充当发行者的开放系统带来真正挑战。首先，即使 token 不可链接，知道用户可访问特定发行者本身是隐私泄露，因为可推断用户符合相关发行标准。如果一个站点能得知你有来自另一站点的 token，那揭示你去过该站点，可能是重大隐私问题。若站点能得知你访问过的发行者集合更严重，因为它成为可用于识别你的指纹。证明陈述的零知识通用技术存在：可证明客户端有来自可接受发行者集合的 token 而不揭示具体哪个。我们称发行者盲化。通用方法常慢，但针对底层密码学定制的专门方法可大幅改善。另一个挑战是站点如何决定信任谁发行 token。发行者行为不端则站点速率限制失效、容量滥用成为可能。但若需防止站点学习用户可访问哪些发行者，站点只知道其受信发行者之一被使用、不知道哪个。这使发行者错误或不当行为难以检测，也使站点难以评估新发行者。解决此挑战对开放性必不可少。信息不足时站点倾向保守发行者选择，可能减少 Anchor 间选择、创造新形式看门人。为解决，站点至少需要一种为每个所用发行者计算聚合分数的方式，大致对应它认为来自该发行者用户的流量中滥用占比。Mozilla 长期投资 Prio 等系统——用多方计算（MPC）保护用户隐私同时启用系统行为聚合测量。Privacy Pass 也难处理速率限制动态调整。token 发行后难以撤销，除非撤销全部活动 token或冒损害用户隐私攻击的风险。站点若能按客户端调整速率限制也有益（更确信客户端良性时提高、检测滥用时撤回访问）。匿名信用 token（Anonymous Credit Tokens，ACT）提供解决此问题的有用构建块。常规 Privacy Pass 方案依赖发行 token 桶，ACT 不同：启用带状态的凭据使用。例如 ACT 凭据可持内部计数器。呈现凭据时站点可检查计数器超阈值并变异它（站点对持有者观感改善或恶化时增减计数器）。关键：确切值从不泄露给站点，防止站点跟踪持有者并确保同一凭据连续呈现不可链接。

**整合。** 那么如何组合这些技术构建开放 Web 上启用隐私保护速率限制的系统？2026 年 5 月我们与 Cloudflare、Chrome 及其他 Web 利益相关者协作参与 W3C CG 会议，开始勾勒我们称为 PACT（Private Access Control Tokens，私有访问控制 token）的设计。速率限制需要起点、锚定的稀缺源。我们称提供此类源的实体为 Anchor。对满足 Anchor 标准的用户（如订阅、良好账户、验证电话号），Anchor 按 Privacy Pass 模型发行 Endorsement token 批次。实践中 Anchor 可以是任何可访问此类信号的网站。Endorsement 向其他站点传达稀缺性。这对简单"授予或拒绝访问"系统足够。但如前所述，我们还要能在访客行为良性时增加访问、否则减少。执行速率限制所需的状态不能存在于 Endorsement，因为 Endorsement 跨越无关站点间信任边界。我们需要可持状态的第二对象，限定于维护它的方。我们称为站点处理速率限制的方为 Moderator，有状态对象为 Credential。Credential 特定于 Moderator；与 Endorsement 不同，我们限制每站点提名单一 Moderator。常见情形站点自己扮演 Moderator，无新实体或信任边界。Moderator 也可是多站点共享的第三方服务，允许这些站点协作共享速率限制。用前节术语：Anchor 是 Endorsement 发行者，Moderator 既验证 Endorsement 又发行 Credential。Moderator 管理速率限制政策：决定信任哪些 Anchor、接受其 Endorsement、回发 Credential。直接揭示哪个 Anchor 支持 Endorsement 会泄露大量用户信息。发行者盲化技术解决：赎回 Endorsement 时 Moderator 只知它来自其信任的 Anchor 之一、不知哪个。Moderator 覆盖多站点时，我们允许 Credential 跨全部呈现，但按任何其他第三方站点方式分区 cookie 与存储。Credential 呈现的不可链接性防止创造新跨站标识符。好处是：一站良行改善 Moderator 覆盖的所有站点访问，坏行为各处削减。网站已可用共享账户系统构建同样能力，所以这不创造锁出用户的新方式，但确实提供无需用户放弃隐私的授权新方式。启用覆盖多站点的 Moderator 带来集中化风险，类似今天反滥用提供商的集中。缓解是 Moderator 选择权留在每站点、受信 Anchor 选择权留在每 Moderator。这不能逆转 Web 已面临的集中压力，但确保此系统不会导致额外锁定：新 Anchor 或新 Moderator 无需与主导厂商协调即可采用。

系统三流程。第一，用户经正常交互、基于 Anchor 对用户的正面看法从 Anchor 接收 Endorsement。对任何给定用户与 Anchor 这是相对罕见操作。毕竟作为稀缺源，Endorsement 不应太易积累。第二，用户到达与 Moderator 协作的站点时，浏览器花费来自 Moderator 信任 Anchor 的 Endorsement 并收到 Credential。呈现隐藏用了哪个 Anchor，Anchor 与 Moderator 都无法追溯 Endorsement 到发行处。Moderator 决定 Credential 初始余额。若用户完全没有合适 Anchor 的 Endorsement，可用现有机制（CAPTCHA、账户创建、联邦登录）同样引导 Credential，系统退化为今天体验而非锁出用户。第三，用户浏览时浏览器呈现 Credential，Moderator 更新 Credential 内部状态。Moderator 可奖励看似良性行为、惩罚可疑活动，但无法跟踪 Credential 使用或在其他站点识别它。撤销从同一机制得出：Moderator 可拒绝返回更新后的 Credential。实践中这一切对用户透明地经 WebAPI 发生，充当 Anchor 或 Moderator 的站点从 JavaScript 调用。理想生态中，用户仅凭已访问站点就在正常浏览中积累 Endorsement，其余流程在移动于 Web 时后台发生，给用户显著更少摩擦。代表用户行动的 AI 智能体滑入同一流程。智能体可携带用户的 Credential——此时用户对智能体行为保持负责，站点无需授予比给用户本人更多访问。或者智能体运营者可运行自己的 Anchor，像其他 Anchor 为人类用户背书那样为智能体背书。站点保留接受哪些 Anchor 的控制，因此无需单独检测机制即可选择如何对待智能体流量。

若干机制结合把关于用户流出的信息保持接近单比特。密码学不可链接性确保连续 Credential 呈现无法互相绑定或与原始发行绑定，因此用户访问无法拼接成历史。每站点绑定单一 Moderator，因此用户持有 Credential 的 Moderator 集永不成跨站指纹。Anchor 到 Credential 交换在隔离浏览上下文发生，因此普通浏览期间站点或其 Moderator 唯一观察到的是 Credential 呈现：站点只学到用户是否有低于速率限制的有效 Credential，或什么也没有。Moderator 更新 Credential 时调整状态而不学习它是什么。发行者盲化给用户的额外隐私使 Moderator 参与更具挑战。因为 Moderator 无法在发行时看到哪个 Anchor 支持 Credential，它不能给强 Anchor 的 Credential 比弱 Anchor 更多访问：这样做本身会泄露用了哪个 Anchor。初始访问必须跨 Moderator 全部 Anchor 池统一，实践中意味着按最弱设定。但这只关乎初始访问：Moderator 可按持有者行为更新凭据，使 Credential 随时间积累访问。构建开放生态还要求站点能对信任的 Anchor 做有效决策。Prio 等多方计算系统实现不损隐私的聚合评分。用户呈现 Credential 时可提供识别所用 Anchor 的加密份额，可私密聚合计算发行者质量。

**下一步。** 我们认为为 PACT 勾勒的架构形状正确，但许多细节仍需厘清，整个系统需要严格隐私与安全分析。我们想在开放中做这些工作。IETF 是底层密码协议的天然场所，W3C 是上层 WebAPI 表面的天然场所。草稿规范准备好即提交这些机构，欢迎生态各方的协作者：浏览器厂商、站点运营者、反滥用提供商与密码社区。若成功，我们认为可提供让 Web 保持开放私密的系统，同时给站点所需的速率限制信号。
