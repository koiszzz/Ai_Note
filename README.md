# 信息源自动整理

本仓库用于抓取信息源，并把内容统一整理成中文 Markdown 笔记。

## 给 LLM 的一句话指令

以后只需告诉 LLM：

> 请按照 README 执行信息源整理。

LLM 收到这句话后，应直接完成下方全部流程，不需要再次询问确认。

## 处理策略：中文源脚本化，外文源逐篇（先读本节再读契约）

先按“是否中文源”分流，可大幅减少逐篇手工工作：

### A. 中文源（原样重排，无翻译）→ 一律用脚本，禁止手工逐篇

以下数据源的内容本身就是简体中文，整理只是“拆条 + 统一模板 + 写 frontmatter + 校验”，全部可由脚本确定性完成：

- 通用中文 RSS 源（脚本 `organize-chinese-rss.mjs`）：虎嗅、华尔街见闻、机核、量子位、美团技术团队、阮一峰的网络日志、小众软件、游戏研究社
- 合集日报（`organize-ai-daily.mjs`）：AI资讯日报
- 合集日报（`organize-chinese-feeds.mjs`）：Horizon Daily（中文摘要）
- 仅标题源（`organize-metadata-only-chinese.mjs <源名>`）：掘金人工智能

中文源的处理方式：

1. 抓取后直接运行中文源脚本（幂等：源文件未变时自动跳过；源文件更新或输出缺字段时自动重写）：
   ```powershell
   node scripts/organize-chinese-rss.mjs --vault="."
   node scripts/organize-ai-daily.mjs "."
   node scripts/organize-chinese-feeds.mjs "."
   ```
2. 脚本已内置逐篇检测（`validate-translated-note.mjs`），检测失败的文章不会写入；脚本产出的笔记无需再逐篇手动校验。
3. 脚本产物写入 `整理/<源>/` 平铺目录后，必须运行迁移脚本归入日期目录（见 5.1），再跑全量审计。
4. 一键串联（整理 → 对账 → 迁移 → 审计）：
   ```powershell
   node scripts/pipeline.mjs --vault="."
   ```
   可用 `--steps=chinese,daily,horizon,reconcile,migrate,audit` 裁剪，`--no-audit` 跳过约 5 分钟的最终审计。

### B. 非中文源（需完整中文翻译）→ 由 LLM 逐篇翻译，脚本只做机械辅助

arXiv 等外文源没有“原样搬运”的捷径，翻译必须由 LLM 完成。以下脚本只减少机械劳动，不代替翻译，也不允许因此跳过任何可读的外文文件：

- `scripts/translate-batch.mjs`：批次预处理。对一批原文自动完成“跨源复用已有翻译 → 生成带完整 frontmatter/哈希/摘要的骨架 → 校验”，LLM 只需填充/审核翻译正文：
  ```powershell
  node scripts/translate-batch.mjs --vault="." --src="信息源/arXiv cs.CV RSS" --limit=10
  ```
  支持 `--reuse-from=源A,源B` 复用其他源已翻译的同标题论文（`--src` 也可传 list 文件）；`--llm=claude` 可批量调用 Claude Code CLI 直接翻译。
- `scripts/reuse-cross-notes.mjs`：跨源复用专用（同一论文出现在多个类别 RSS 时，如 cs.AI/cs.LG/cs.CV/cs.CL）。`--report` 查看哪些条目可复用及内容是否一致，`--apply` 一键复制翻译并改写 `source/original_file/source_note/source_sha256` 四个字段：
  ```powershell
  node scripts/reuse-cross-notes.mjs --vault="." --target="arXiv cs.CV RSS" --report
  node scripts/reuse-cross-notes.mjs --vault="." --target="arXiv cs.CV RSS" --apply
  ```
- `scripts/reconcile-sha.mjs`：全库哈希对账（防回归）。输出中 `source_sha256` 与当前源文件不一致时列出；`--fix` 自动更新哈希：
  ```powershell
  node scripts/reconcile-sha.mjs --vault="." --fix
  ```

#### B.1 防重复搬运（强制，禁止同一翻译反复生成）

以下规则防止“换日期目录、换数据源或重跑脚本就再次生成/再次搬运已有翻译”：

- **全树查重**：处理任何外文条目之前，必须先在整个 `整理/<源>/` 输出树（含全部日期子目录）中按 `source_sha256` 查找是否已存在对应笔记；存在即视为已整理，禁止重新翻译或重新生成。脚本（`translate-batch.mjs`、`reuse-cross-notes.mjs --apply`）已内置跨日期目录查重；LLM 手工处理时也必须全树检索，不得只查单个日期目录或数据源根目录后误判“未整理”。
- **输出落位**：`translate-batch.mjs` 与 `reuse-cross-notes.mjs --apply` 的产物一律写入 `整理/<源>/<YYYYMMDD>/` 日期目录，禁止写入 `整理/<源>/` 根目录；运行后必须执行迁移脚本（见 5.1）规范化并核对数量，根目录不得残留平铺文件。
- **一份翻译原则**：同一篇论文（按 `original_file` 文件名去掉扩展名后小写归一化判定）在整个 `整理/` 中只允许存在一份翻译内容。同一论文出现在多个数据源（如 arXiv 类别交叉）时，通过复制现有翻译并改写 `source`、`original_file`、`source_note`、`source_sha256` 四个字段完成，不得重新翻译。
- **复用后对账**：跨源复用写入的 `source_sha256` 必须是目标源原文件的当前哈希；每次复用或手工整理后运行 `reconcile-sha.mjs --fix`，确保无哈希漂移。
- **重复副本处置**：发现同一 `source_sha256` 出现在多个文件时，保留日期目录内的文件，删除其余副本，再重新审计；禁止保留根目录副本“备用”。
- **历史遗留说明**：早期手工复用产生的同一论文翻译可能存在模板或措辞差异（内容不完全一致），这不影响审计通过，属允许状态；今后统一用脚本复用保证一致，不要再手工复制粘贴。

### C. 分流边界（必须遵守）

- 中文源即使量再大也必须用脚本跑完，禁止“只挑几篇手工做”。
- 外文源即使有脚本辅助，翻译正文仍必须由 LLM 完成；不得因为“已有骨架/已复用”就跳过翻译，也不得把 `待翻译` 占位当作完成（见最终完成闸门）。
- 无论用哪种方式处理，最终都必须满足：迁移脚本“数量核对”全部通过 + 全量审计 `ok: true` 且 `pending/changed/failed` 均为 0。

## 最高优先级：完整执行契约（禁止提前结束）

本节是整个任务的最高优先级执行约束。模型必须先完整读取本 README，再开始工作；不得只执行其中一部分，也不得用后续章节的任何表述降低本节要求。

### 唯一任务目标

任务目标不是“完成一批”“尽可能多处理”或“记录当前进度”，而是：

> 抓取完成后，对本次扫描到的所有可读取待处理文件逐一完成解析、完整中文翻译或中文重排、写入、逐篇校验和最终审计，直到待处理数量为 0。

输出笔记数量不能代替源文件覆盖率。合集拆分后可能由少量源文件产生大量笔记，因此必须以去重后的 `original_file` 覆盖情况和 `source_sha256` 为完成依据。源文件仅在整理后新增或改动 `发布时间` 标记行（其余内容与哈希一致）时，视为哈希一致，不判定为未整理。

### 必须持续执行的循环

模型必须按以下状态机持续执行，不能自行跳出：

1. 本次任务开始时抓取一次最新信息。
2. 扫描全部源文件，建立明确的待处理队列，并记录待处理总数。
3. 从队列中逐个或分批处理文件；每篇写入后立即运行译后检测。
4. 每完成一个批次，重新扫描并重新计算 `pending`、`changed`、`failed`，不能凭记忆或输出文件数量估算。
5. 若 `pending > 0` 或 `changed > 0`，立即开始下一批，回到步骤 3。
6. 只有通过“最终完成闸门”后，才允许发送最终答复并结束任务。

批次只是控制上下文和便于校验的内部手段，批次结束绝不是任务结束。模型可以压缩上下文、重读队列或更新运行记忆，但完成这些动作后必须继续下一批。

允许在处理过程中用 commentary 报告真实进度，但进度消息之后必须继续调用工具处理队列；进度消息不能替代后续工作，也不能使用 final 渠道发送。

### 明确禁止的提前结束行为

以下行为全部视为任务失败：

- 只处理中文文件、短文件、仅标题文件或容易脚本化的来源，把可正常读取的外文文件留到以后。
- 只完成抓取、扫描、脚本编写、格式转换、合集拆分或质量审计，没有处理全部待整理正文。
- 在 `pending > 0` 时发送 final、完成报告、阶段性完成通知或 inbox 完成通知。
- 以“本轮已处理若干篇”“剩余内容下次继续”“供下次从这里继续”等措辞主动结束。
- 因文件数量多、预计耗时长、上下文需要压缩、已经工作较久或本批结果已通过校验而停止。
- 把更新自动化记忆、保存 checkpoint 或等待下一次 cron 运行当作结束当前任务的理由。
- 用摘要、节选、占位文字、英文原文副本或批量机器改写冒充完整中文翻译。

如果宿主系统发生模型无法控制的硬中断，已完成文件和运行记忆可供恢复；但只要模型仍能继续调用工具和写入文件，就不得主动选择停止。下一次恢复后也必须立即从剩余队列继续，而不是重复已完成内容或再次只做盘点。

### 最终完成闸门

发送最终答复前，模型必须重新读取本节并执行全量审计。以下条件必须同时满足：

- `pending_source_files = 0`：不存在未被有效整理结果覆盖的可读取源文件。
- `changed_source_files = 0`：不存在 `source_sha256` 与当前原文件不一致的整理结果。原文件仅新增或改动 `发布时间`（published）标记行、其余内容一致时视为一致，不进入 `changed` 或 `pending`。
- `failed_outputs = 0`：所有新建或更新的输出均通过逐篇译后检测。
- 每个可读取源文件都至少有一个有效输出；合集文件的每个独立条目都有独立输出。
- 所有非简体中文标题和正文均已完整翻译；没有只翻译标题、摘要或前几段的文件。
- 所有异常都确实属于原文件损坏、正文为空、编码无法恢复或内容客观不可读取，并已逐文件写明原因；可正常读取的外文文件不得列为异常。

任何一项不满足时，审计结果只能作为内部进度信息，模型必须继续处理，禁止据此结束任务。

审计统计至少应包含以下字段，并按当前文件系统重新计算：`total_source_files`、`covered_source_files`、`pending_source_files`、`changed_source_files`、`output_articles`、`passed_outputs`、`failed_outputs`。其中 `covered_source_files` 必须按有效且哈希一致的 `original_file` 去重（原文件仅新增或改动 `发布时间` 标记行时视为哈希一致）；若源文件是合集，只有所有已识别的 `source_fragment` 都存在并通过检测后，该源文件才算已覆盖。

### 强制审计命令（退出前必须调用）

完成所有整理工作后，模型必须在 Vault 根目录调用以下只读审计脚本：

```powershell
node scripts/audit-organized-notes.mjs --vault="."
```

该命令是是否允许结束任务的唯一机器判定，模型不得用自行统计、历史记忆、抽样检查或自然语言判断替代。退出规则如下：

- 退出码 `0` 且 JSON 中 `ok: true`：完成闸门通过，允许发送最终答复。
- 退出码 `1` 或 JSON 中 `ok: false`：任务尚未完成。模型必须读取 `details`，修复失败输出并继续处理全部待整理文件，然后重新运行审计。
- 退出码 `2`：审计命令或运行环境出错。模型必须先修复审计执行问题并重新运行；不得把审计工具错误当作整理完成。

审计通过后，如果模型又修改、添加或删除了 `信息源/`、`整理/` 中的任何文件，之前的结果立即失效，必须重新运行审计。最终答复中引用的数字必须来自最后一次成功审计。

严格禁止跳过脚本、伪造退出码、截断或忽略失败详情、用 `|| true` 等方式吞掉非零退出码、为了让审计通过而放宽检查规则，或在审计未通过时发送任何形式的 final。审计失败是“继续工作”的信号，不是“报告部分完成并退出”的理由。

## 强制要求：由 LLM 自身直接翻译

翻译是执行本任务的 LLM 本身必须完成的工作，不依赖任何翻译 API、翻译软件、本地翻译引擎、第三方服务或额外工具。

- LLM 必须读取原文，并使用自身的语言理解与生成能力直接输出简体中文译文。
- “没有翻译接口”“没有本地翻译引擎”“没有安装翻译工具”均不构成阻塞、异常或跳过理由。
- 不得等待用户配置翻译服务，不得要求用户提供 API Key，也不得因为缺少翻译工具而只处理原本就是中文的文件。
- 脚本只负责抓取、扫描、格式转换、清理、哈希与文件写入等机械操作；脚本不能代替 LLM 完成翻译。
- 对非中文文件，LLM 必须逐篇直接翻译。文件较多时可以分批处理，但必须在同一次任务中持续执行后续批次，直到所有待处理文件完成，不能把剩余文件留作“以后处理”。
- 只有原文件损坏、正文为空、编码无法恢复或内容超出当前模型可读取范围时，才可列为异常；列为异常时必须写明具体文件和原因。

## 自动执行流程

### 1. 抓取最新信息

部分数据源（如 Hugging Face、GitHub Pages 上的源）需要代理才能连通。若直连抓取失败，先设置代理再执行命令：

```powershell
$env:HTTP_PROXY="http://localhost:10800"
$env:HTTPS_PROXY="http://localhost:10800"
$env:NODE_USE_ENV_PROXY="1"
```

`NODE_USE_ENV_PROXY=1` 让 Node 内置 fetch 直接走代理（Node 24+）；未设置时脚本会在 fetch 超时后自动用 curl 回退，curl 同样读取 `HTTP_PROXY`/`HTTPS_PROXY`。代理仅解决连接类失败；返回 404、正文为空等数据源本身的问题不会因代理而恢复。

在仓库根目录执行：

```powershell
node scripts/fetch-ai-feeds.mjs --vault="."
```

脚本会把新内容写入 `信息源/`。除非命令报错，否则不要跳过此步骤。若个别数据源抓取失败，记录失败项，并继续处理其余文件。

数据源清单维护在 `scripts/fetch-ai-feeds.mjs`，每个源明确标注一种抓取规则：`rss`（RSS 2.0/RDF）、`atom`（Atom feed）或 `html`（网页正文）。写入前脚本会根据 HTTP/XML/HTML 声明解码（含 GBK/GB18030 回退），检查替换字符、编码转义、根节点、条目标题和正文；只验证不写入时执行：

```powershell
node scripts/fetch-ai-feeds.mjs --vault="." --validate --limit=1
```

验证失败的数据源会被跳过，不会产生原始笔记。

### 1.1 抓取后立即审计并返回待处理文件列表

抓取命令结束后，模型必须立即运行一次全量审计，不能直接开始整理：

```powershell
node scripts/audit-organized-notes.mjs --vault="." --max-details=1000000
```

审计命令即使以退出码 `1` 结束，也必须读取并解析它输出的完整 JSON；退出码 `1` 表示当前仍有待处理内容，不表示命令失败。只有退出码 `2` 才表示审计执行错误，模型必须先修复执行问题。

模型必须从审计 JSON 建立本次任务的唯一待处理文件列表：

1. 将 `details.pending_sources.shown` 中的每个源文件加入列表。
2. 将 `details.changed_sources.shown` 中的每个源文件加入列表；这些文件必须按“原文件已更新”重新整理。
3. 检查 `details.missing_fragments.shown`；合集文件必须把其中每个缺失的 `source_fragment` 作为独立整理项加入该源文件的子清单。
4. `shown` 的 `omitted` 必须为 `0`。如果不是 `0`，必须提高 `--max-details` 后重新审计，禁止使用被截断的列表。
5. 返回给调用方本次审计统计和完整待处理文件列表，至少包括每个文件的 Vault 相对路径、所属数据源、处理类型（新整理/更新/缺失合集条目）和合集条目标题（如有）。

后续整理工作必须严格以这份列表为任务队列：逐项处理，不得跳过、凭记忆补充、只处理列表中的中文文件，或用输出笔记数量代替列表覆盖率。每完成一个批次，必须重新运行同一审计命令，用最新审计结果替换旧列表；只要新列表仍有项目，就继续处理下一批。待处理列表为空不等于任务完成，还必须通过本 README 规定的最终完成闸门。

当前仓库的待处理列表必须以审计命令的最新 JSON 为准，不要把 README 中的示例、历史输出或模型记忆当作清单。

### 2. 按待处理列表扫描和整理文件

递归扫描 `信息源/` 下的文件，处理以下类型：

- Markdown：`.md`、`.markdown`
- HTML：`.html`、`.htm`
- 纯文本：`.txt`

忽略隐藏文件、临时文件和无法确认是正文的二进制文件。

`信息源/` 是原始资料区：不得删除、移动、覆盖或重命名其中的文件。

### 3. 转换与翻译

对每个文件执行以下规则：

1. HTML 文件先转换为 Markdown，去除脚本、样式、导航、广告等无关内容，保留标题、正文、列表、表格、引用、代码块、图片和链接。
2. Markdown 文件保留有效的 Markdown 结构，清理重复标题、多余空行、乱码字符和明显的抓取噪声。
3. 判断标题和正文的主要语言。只要主要内容不是简体中文，就将标题和正文完整翻译为自然、准确的简体中文。
4. 代码、命令、URL、文件路径、数学公式、产品名、组织名、论文编号和人名原则上保留原文；专业术语首次出现时可写为“中文译名（English）”。
5. 不得编造、扩写或改变原文结论。内容缺失或无法可靠解析时，应明确标注，而不是猜测。
6. 如果原文已经是中文，仍需按统一模板重新排版。

本节的“翻译”均指 LLM 直接进行翻译，不得改为调用或等待翻译接口，也不得仅生成机器占位文本、英文原文副本或“待翻译”标记。

### 译后质量检查（强制）

每篇非中文文件翻译完成后，LLM 必须重新读取最终 Markdown 文件并检查译文。检查通过之前，该文件不得计入“已整理”或“已翻译”。

每翻译并写入一篇文章后，必须立刻运行检测工具，禁止等全部文章完成后再统一抽查：

```powershell
node scripts/validate-translated-note.mjs "整理/数据源/YYYYMMDD/译文.md" --source="信息源/数据源/原文.md" --attempt=1
```

检测器会输出 JSON。`ok: true` 且进程退出码为 `0` 才表示通过；退出码为 `1` 表示译文不合格，LLM 必须依据 `errors` 修正或重新翻译，然后执行第二次检测：

```powershell
node scripts/validate-translated-note.mjs "整理/数据源/YYYYMMDD/译文.md" --source="信息源/数据源/原文.md" --attempt=2
```

第二次仍失败时，JSON 会返回 `manual_review_required: true`。此时 LLM 必须亲自重新读取原文和译文，逐段检查并修正，不能因为脚本失败就跳过文章。

如果 LLM 确认剩余错误只是检测器对专业英文术语、参考文献或中英混排的误判，可以在第二次或之后的人工复核中执行：

```powershell
node scripts/validate-translated-note.mjs "整理/数据源/YYYYMMDD/译文.md" --source="信息源/数据源/原文.md" --attempt=2 --manual-approved
```

`--manual-approved` 只能放行可人工判断的语言占比、长度或外文段落警报；缺失结构、中文过少、十六进制、Unicode 转义、Base64、乱码、零宽字符和占位文本等硬错误永远不能人工放行，必须修正后重新检测。

人工放行后必须把复核证据写入该整理稿的 YAML，否则最终审计仍会判定失败：

```yaml
validation_attempt: 2
validation_manual_approved: true
validation_manual_approval_reason: "已逐段对照原文；剩余警报仅来自参考文献、专业术语或允许保留的英文专名。"
```

不得在未实际逐段复核时写入这些字段，也不得复制同一理由批量放行不同文章。

必须逐项检查：

1. **确实是中文**：标题、摘要和正文的自然语言内容应以简体中文为主。代码块、命令、URL、公式、专有名词和参考文献不参与语言占比判断。
2. **不是编码文本**：正文不得出现大段 `0xE4 0xB8...`、`\xE4\xB8...`、`\u4E2D\u6587`、HTML 数字实体、Base64 或其他用编码代替中文正文的内容。
3. **没有乱码**：不得出现大量 `�`、空方框、问号替代字符、异常控制字符、零宽字符、错误解码片段或无意义符号串。
4. **翻译完整**：不得只翻译标题、摘要或第一段；除允许保留的技术内容外，正文不能残留大段未翻译外文。
5. **语义正确**：将译文与原文逐段对照，核对人物、组织、数字、日期、单位、否定关系、因果关系、技术术语和结论，确认没有遗漏、反转、臆造或明显误译。
6. **结构正常**：Markdown 标题、列表、表格、引用、代码块、链接和图片应完整可读，不得把正文错误地塞进 YAML、代码块或一行超长文本。
7. **长度合理**：译文不能异常为空或明显短于原文。允许因语言差异而长度变化，但不得用摘要冒充完整翻译。

建议的自动检测只能用于发现问题，不能替代 LLM 对语义的复核。至少检测以下异常特征：

```text
连续十六进制：(?:0x|\\x)[0-9A-Fa-f]{2}
Unicode 转义：\\u[0-9A-Fa-f]{4}
替换字符：�
过长 Base64：连续 100 个以上 Base64 字符
外文残留：排除代码和链接后，存在连续多个完整外文段落
```

如果检查失败：

- 立即从原文件重新翻译或修正失败段落，然后重新执行全部检查。
- 禁止仅删除乱码或编码文本后就当作完成；必须恢复对应的正确中文内容。
- 修正后的文件必须再次完整读取并与原文核对。
- 多次修正仍无法得到可靠中文译文时，不得输出伪造的“合格文件”，应将该原文件列入异常报告并说明具体问题。

### 4. 统一排版

每个结果文件必须从 YAML frontmatter 开始，第一行必须是 `---`，不得在 frontmatter 前写标题、说明或其他内容。`published` 是必填属性，并且必须作为 frontmatter 的第一个属性维护；它表示文章的原始发布日期，不是整理日期。日期统一使用 `YYYY-MM-DD`。如果原文没有明确发布日期，必须根据原文上下文或来源页面谨慎判断，不能随意使用当前日期；确实无法确认时保留 `published: null`，并在来源信息中说明日期缺失。日期目录统一按 `published → processed → 当天` 决定（见 5.1 迁移脚本），不使用 `unknown` 目录。

除 `published` 外，没有的信息项可以省略，但不得省略 `published`。

```markdown
---
published: YYYY-MM-DD
title: 中文标题
source: 数据源名称
original_file: 信息源/相对路径/原文件名
source_note: "[[信息源/相对路径/原文件名]]"
source_sha256: 原文件的 SHA-256 值
original_url: https://example.com/article
processed: YYYY-MM-DD
language: zh-CN
---

# 中文标题

> [!info] 来源信息
> - 数据源：数据源名称
> - 作者：作者或机构
> - 发布时间：原文发布时间
> - 原文链接：[打开原文](https://example.com/article)
> - Vault 原文件：[[信息源/相对路径/原文件名|查看原始文件]]

## 摘要

用 3～5 个要点概括原文的核心信息。摘要必须忠于原文。

## 正文

重新排版后的完整中文正文。

## 关键词

#关键词一 #关键词二 #关键词三
```

排版要求：

- 全文使用 UTF-8 和简体中文标点。
- 标题层级从 `#` 开始且连续，不要跳级。
- 段落保持适当长度，列表、引用、表格和代码块使用标准 Markdown。
- 保留原文中的重要链接和图片；相对链接应尽量转换为可用链接。
- 删除网页菜单、订阅提示、Cookie 提示、分享按钮、版权页脚等非正文内容。
- 不要把摘要当作正文；若原文件只有摘要，则在正文中注明“原始来源仅提供摘要”。

### Obsidian 双链关联

每篇整理稿必须通过 Obsidian Wikilink 与其原始文件建立关联：

- YAML 的 `source_note` 保存原文件的 Wikilink，便于在属性视图中查看关联。
- 正文“来源信息”中的“Vault 原文件”提供可点击链接。
- 原文件为 Markdown 时，链接可以省略 `.md` 扩展名，例如 `[[信息源/GitHub Blog/文章标题|查看原始文件]]`。
- 原文件为 HTML、TXT 等非 Markdown 文件时保留扩展名，例如 `[[信息源/网页/example.html|查看原始文件]]`。
- 路径必须相对于 Vault 根目录，不得写 Windows 绝对路径。
- 不要修改原文件。Obsidian 会自动把整理稿显示在原文件的“反向链接”面板中，从而形成可双向导航的关联。
- 若文件名中包含 `|`、`#`、`^` 或方括号等可能破坏 Wikilink 的字符，应先生成安全的输出名称，并确保链接仍能准确解析到原文件。

### 5. 写入整理目录

结果统一保存到 `整理/`，并按“数据源 / 发布日期 / 文章”组织目录。每篇文章的输出路径必须符合以下结构：

```text
信息源/Google Blog Feed/Example.html
→ 整理/Google Blog Feed/20260806/Example.md
```

日期目录按以下优先级确定：frontmatter 的 `published`（默认优先）→ `processed` → 都没有时使用当天日期；格式统一为 `YYYYMMDD`，不使用 `unknown` 目录。合集拆分后，每篇文章都必须根据自己的发布日期进入对应日期目录，不能继续把多篇文章放在数据源根目录下。

### 5.1 存量整理稿迁移与数量核对（强制）

整理脚本（`organize-chinese-rss.mjs`、`organize-ai-daily.mjs`、`organize-chinese-feeds.mjs`、`organize-metadata-only-chinese.mjs` 等）会把结果先写入 `整理/<数据源>/` 平铺结构，因此每次运行整理脚本后都必须执行迁移脚本，把平铺文件规范化到日期目录（不限于历史遗留文件，脚本产物同样适用）；不允许 LLM 手工搬移或凭记忆估算数量。执行：

```powershell
node scripts/migrate-organized-notes.mjs --vault="."
```

该脚本完成以下工作：

1. 只处理平铺在 `整理/<数据源>/` 根目录下的 `.md` 文件（已进入 `YYYYMMDD` 日期目录的文件不处理）。
2. 按以下优先级确定日期目录：frontmatter 的 `published`（默认优先）→ `processed` → 都没有时使用当天日期；日期统一格式化为 `YYYYMMDD`。
3. 覆盖式移动到 `整理/<数据源>/<YYYYMMDD>/<文章>.md`：目标文件已存在时直接覆盖，不产生 `-N` 后缀副本。
4. 移动完成后，在每个数据源目录（`整理/<数据源>/`，含其下全部日期子目录）内按“内容 SHA-256 + 文章标题（frontmatter `title`）”查重：同一数据源目录内存在哈希与标题都一致的文件时，保留刚移入的文件（或按文件名排序的第一个），删除其余重复文件。
5. 脚本只做机械操作（解析 frontmatter、移动、覆盖、去重删除），不修改正文与源文件。

可用参数：

```powershell
node scripts/migrate-organized-notes.mjs --vault="." --source="量子位"  # 只处理指定数据源（小范围测试）
node scripts/migrate-organized-notes.mjs --vault="." --dry              # 只打印迁移计划，不写盘
node scripts/migrate-organized-notes.mjs --vault="." --check-only       # 只核对当前状态，不迁移
```

**迁移后必须检查数量是否对得上（强制）**：脚本输出会列出每个文件的迁移明细（含日期来源：published/processed/当天），并在末尾给出“数量核对”四项判定。LLM 必须逐项核对以下条件，任何一项不满足即继续修复并重新运行，禁止用 `|| true` 等方式吞掉非零退出码：

- 失败数为 0。
- 迁移后文件总数 = 迁移前文件总数 − 删除的重复文件数 − 覆盖更新的文件数（覆盖更新会同时移除平铺文件，因此总数减少 1）。
- 迁移后数据源根目录不得残留任何 `.md` 文件。
- 每个数据源目录内（跨日期子目录）不得存在哈希与标题一致的重复文件。

脚本是幂等的：已全部迁入日期目录后重复运行，待迁移数为 0，输出“核对结果：通过（ok: true）”且进程退出码为 0 才算通过。迁移完成后，LLM 必须重新运行 `scripts/audit-organized-notes.mjs` 全量审计，确认 `pending_source_files`、`changed_source_files`、`failed_outputs` 均为 0；迁移改变了 `整理/` 中的任何文件后，之前通过的审计结果一律作废，必须重新审计。迁移后的这次审计同时作为 1.1 批次循环审计的一部分，最终完成闸门以最后一次审计结果为准。

文件名规则：

- 输出扩展名统一为 `.md`。
- 优先使用简洁的中文标题作为文件名。
- 移除 Windows 文件名不允许的字符：`\ / : * ? " < > |`。
- 文件名过长时合理缩短，但不要丢失主题含义。
- 若不同原文件生成同名文件，在文件名后添加短来源名或日期，禁止相互覆盖。

### 合集文件必须拆分

整理任何源文件时，LLM 都必须先判断它是否由多篇独立文本或文章合并而成。若判断为多份合并，必须直接识别文章边界并拆分为多篇独立笔记，不能把整份合集直接整理成一篇笔记；之后每篇文章分别经过排版、翻译、写入和检测。即使文件没有明确标注“合集”，只要存在多个独立标题、来源链接、日期或相互独立的正文单元，也应按实际文章边界拆分。

- Horizon Daily 文件按每个 `### [文章标题](原文链接)` 拆分；`##` 标题是分类名称，不是文章。
- AI资讯日报文件按 `###` 分类下的每个 `- 文章标题。正文` 列表项拆分；列表项后紧跟的图片也归入该文章。
- 每个拆分结果只包含一篇文章，并使用该文章标题命名。
- 每篇拆分结果保留原始日报的 `original_file`、`source_note` 和 `source_sha256`，并增加 `source_fragment` 记录原条目标题。
- 每篇保留自己的原文链接、正文、参考链接、标签以及所属分类。
- 同一日报拆出的文章使用日期作为文件名后缀，避免不同日期出现同名文章时互相覆盖。
- 其他来源若出现多个一级或三级文章条目、重复的独立标题和原文链接，也应按实际文章边界拆分，不能只为 Horizon 编写特例后忽略其他合集。
- 拆分后的每一篇都必须单独运行 `validate-translated-note.mjs`；不能只检测合集原文件或随机抽查其中一篇。

Horizon 中文合集可运行现有拆分整理脚本：

```powershell
node scripts/organize-chinese-feeds.mjs "."
```

该脚本会按 `###` 条目输出独立笔记，并在写入每篇笔记前调用同一检测器。脚本检测失败的文章不会写入，LLM 必须根据日志自行检查和修正。

AI资讯日报合集可运行：

```powershell
node scripts/organize-ai-daily.mjs "."
```

该脚本会按分类下的列表项输出独立笔记，并记录 `source_fragment`、原始文件哈希和原始日报双链；原始文件未变化时会跳过已有文章（跳过范围包含已迁入日期目录的产物，不会重复生成）。

上述两个整理脚本在写入每篇笔记前都已内置调用同一检测器，检测失败的文章不会写入；脚本产出的笔记无需再逐篇手动运行 `validate-translated-note.mjs`（最终审计会全量兜底）。仅对 LLM 手工翻译或重排的笔记，必须逐篇执行本节（译后质量检查）的检测。

### 6. 增量处理与校验

- 通过 YAML 中的 `original_file` 判断文件是否已经整理，并用 `source_sha256` 判断原文件是否发生变化。
- 已整理且原文件 SHA-256 未变化时跳过，避免重复翻译和重复生成；判断须覆盖 `整理/<源>/` 整棵输出树（含全部日期子目录），禁止只查单个日期目录后误判未整理（见 B.1 防重复搬运）。
- 原文件有更新时，重新生成对应结果；不要改动其他已整理笔记。
- 写入后检查 YAML、标题、正文、链接和 Markdown 语法是否完整。
- 对所有新建或更新的译文执行“译后质量检查”；检测到编码文本、乱码、外文残留或语义错误时必须修正并重新检查。
- 保存每篇译文后立即运行 `scripts/validate-translated-note.mjs`，不得跳过、延后或只做抽样检测。
- 对合集先拆分，再逐篇整理和检测；合集内每个条目都计入文章总数。
- 不得在 `整理/` 之外创建整理结果或中间文件。
- 任务完成条件是所有可读取的待处理文件都已整理，并通过“最终完成闸门”；仅完成中文文件、仅扫描文件或留下可正常读取的外文文件，都不得报告任务完成或主动结束任务。

## 完成时的回复格式

只有“最终完成闸门”的全部条件满足后，才可向用户发送以下最终报告。闸门未通过时不得套用此格式发送阶段性报告，也不得发送其他形式的 final：

```text
信息源整理完成：
- 抓取：新增 N 个，跳过 N 个，失败 N 个数据源
- 源文件覆盖：N/N 个
- 完成闸门：待处理 0 个，源文件更新待重做 0 个，检测失败 0 篇
- 整理：新增 N 篇，更新 N 篇，跳过 N 篇
- 翻译：N 篇
- HTML 转 Markdown：N 篇
- 译后检查：通过 N 篇，修正 N 篇，失败 N 篇
- 异常：无（或列出具体文件与原因）
- 输出目录：整理/
```

即使没有新增文件，也要明确回复“已执行脚本并完成扫描，本次没有需要新增或更新的内容”。
