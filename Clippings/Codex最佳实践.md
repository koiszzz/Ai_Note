开始使用 Codex 和行之有效的实践方法，以获得更好的结果

如果您是 Codex 或编码代理的新手，本指南将帮助您更快地获得更好的结果。它涵盖了使 Codex 在命令行界面[(CLI)](/docs/codex/cli)、[集成开发环境 (IDE) 扩展](/docs/codex/ide)和[ChatGPT 桌面应用程序](/docs/app)中更高效的核心习惯，内容涉及提示和规划、验证、多级控制点 (MCP)、技能和计划任务等各个方面。

Codex 的最佳使用方式是，不要把它当作一次性助手，而要把它当作一个队友，随着时间的推移进行配置和改进。

思考这个问题的一个有用方法是：从正确的任务背景开始，利用`AGENTS.md`持久的指导，配置 Codex 以匹配你的工作流程，将外部系统与 MCP 连接起来，将重复性工作转化为技能，并实现稳定工作流程的自动化。

## 首次使用效果显著：语境和提示

即使提示不够完美，Codex 也已经足够强大，能够发挥作用。你通常只需极少的设置，就能给它一个难题，并获得可靠的结果。清晰的[提示](/docs/prompting)并非获取价值的必要条件，但它确实能提高结果的可靠性，尤其是在大型代码库或高风险任务中。

如果你在一个大型或复杂的代码库中工作，最大的突破在于为 Codex 提供正确的任务上下文和清晰的结构，以便更好地完成你想要的工作。

一个好的默认做法是在提示中包含以下四项内容：

- **目标：**你想要改变什么或建立什么？
- **上下文：**哪些文件、文件夹、文档、示例或错误与此任务相关？您可以使用 @ 符号提及特定文件作为上下文。
- **限制：** Codex 应该遵循哪些标准、架构、安全要求或惯例？
- **完成条件：**任务完成之前应该满足哪些条件，例如测试通过、行为改变或错误不再重现？

这有助于 Codex 保持范围明确，减少假设，并产出更容易审查的作品。

根据任务难度选择合适的推理级别，并测试哪种级别最适合您的工作流程。不同的用户和任务需要不同的设置才能达到最佳效果。

- 低优先级，适用于速度快、范围广的任务
- 对于更复杂的更改或调试，请使用中等或高设置。
- 极高，适用于长时间、需要主动思考和推理的任务

为了更快地提供上下文，请尝试在 ChatGPT 桌面应用程序中使用语音听写功能来口述您希望 Codex 执行的操作，而不是键入它。

## 首先要为困难的任务做好计划。

如果任务复杂、模糊或难以描述，请让 Codex 在开始编码之前进行规划。

以下几种方法效果不错：

**使用计划模式：**对于大多数用户来说，这是最简单有效的选择。计划模式允许 Codex 收集背景信息、提出澄清问题，并在实施前制定更完善的计划。使用`/plan`或Shift+切换Tab。

**请 Codex 对您进行面试：**如果您对想要实现的功能有一个大致的想法，但不确定如何准确描述，可以先请 Codex 向您提问。告诉它挑战您的假设，并在编写代码之前将模糊的想法转化为具体的概念。

**使用 PLANS.md 模板：**对于更高级的工作流程，您可以配置 Codex 以遵循`PLANS.md`执行计划模板，从而处理耗时更长或包含多个步骤的工作。更多详情，请参阅[执行计划指南](/cookbook/articles/codex_exec_plans)。

## 使指南可重复使用`AGENTS.md`

一旦某种提示模式奏效，下一步就是停止手动重复该模式。这时[AGENTS.md 文件](/docs/agent-configuration/agents-md)就派上用场了。

您可以将其视为`AGENTS.md`面向代理的开放格式 README 文件。它会自动加载到上下文中，是您和您的团队在代码库中如何定义 Codex 工作方式的最佳场所。

好的`AGENTS.md`封面：

- 仓库布局和重要目录
- 如何运行该项目
- 构建、测试和代码检查命令
- 工程惯例和公关预期
- 约束和禁止规则
- 完成工作的含义以及如何验证工作

CLI 中的斜杠命令`/init`是快速启动命令，用于`AGENTS.md`在当前目录中搭建一个初始项目。这是一个很好的起点，但您应该根据团队实际的构建、测试、审查和发布代码的方式对结果进行编辑。

您可以创建`AGENTS.md`不同层级的文件：一个全局文件`AGENTS.md`用于设置个人默认值（位于根目录下）`~/.codex`，一个仓库级别的文件用于设置共享标准，以及子目录中更具体的文件用于设置本地规则。如果当前目录附近有更具体的文件，则以该文件的规则为准。

务必注重实用性。一份简明扼要、准确无误的`AGENTS.md`文件比一份充斥着模糊规则的长篇文件更有用。先从基础入手，只有在发现反复出现的错误后才添加新规则。

如果`AGENTS.md`文件变得过大，请保持主文件简洁，并引用特定任务的 Markdown 文件来处理规划、代码审查或架构等事项。

如果 Codex 两次犯同样的错误，就要求它进行回顾和更新 `AGENTS.md`。指导意见应保持实用性，并基于实际遇到的问题。

## 配置 Codex 以确保一致性

配置是确保 Codex 在不同会话和界面上行为一致的主要方法之一。例如，您可以设置模型选择、推理工作量、沙盒模式、审批策略、配置文件和 MCP 设置的默认值。

一个好的起始模式是：

- 保留个人默认设置`~/.codex/config.toml`（在 ChatGPT 桌面应用程序中，**设置 > 配置 > 打开 config.toml 文件）。**
- 保持仓库特定的行为`.codex/config.toml`
- 仅在特殊情况下（如果您使用 CLI）才使用命令行覆盖。

[`config.toml`](/docs/config-file/config-basic)您可以在此处定义持久性首选项，例如 MCP 服务器、多代理设置和功能标志。特定于配置文件的覆盖设置保存在单独的`$CODEX_HOME/profile-name.config.toml`文件中。

Codex 内置操作系统级别的沙箱机制，并提供两个关键控制选项。审批模式决定 Codex 何时请求用户许可才能运行命令，而沙箱模式则决定 Codex 是否可以对目录进行读写操作，以及代理程序可以访问哪些文件。

如果您是编码代理的新手，请从默认权限开始。默认情况下，保持严格的审批和沙盒机制，然后在明确需要后，仅对受信任的存储库或特定工作流程放宽权限。

请注意，CLI、IDE 扩展和 ChatGPT 桌面应用程序共享相同的配置层。更多信息请参阅[示例配置](/docs/config-file/config-sample)页面。

尽早针对您的实际环境配置 Codex。许多质量问题实际上都是配置问题，例如工作目录错误、缺少写入权限、模型默认值错误或缺少工具和连接器。

## 通过测试和审查提高可靠性

不要仅仅要求 Codex 做出更改。还要要求它在需要时创建测试，运行相关检查，确认结果，并在接受更改之前审查更改内容。

Codex 可以帮你完成这个循环，但前提是它知道“好”的标准是什么。这个指导可以来自提示符或`AGENTS.md`……

这可能包括：

- 编写或更新变更测试
- 运行正确的测试套件
- 检查代码检查、格式检查或类型检查
- 确认最终行为与请求相符
- 检查差异是否存在错误、回归或风险模式

在 ChatGPT 桌面应用程序中切换差异面板，即可直接在本地[查看更改](/docs/code-review?surface=app)。点击特定行即可提供反馈，这些反馈将作为上下文信息传递给下一轮 Codex 处理。

这里一个很有用的选项是斜杠命令`/review`，它提供了几种代码审查方式：

- 针对 PR 式审查的基础分支进行审查
- 查看未提交的更改
- 查看提交记录
- 使用自定义审核说明

如果您和您的团队有一个`code_review.md`文件，并在其中引用了该文件`AGENTS.md`，Codex 也可以在审核过程中遵循该指南。对于希望在所有代码库和贡献者之间保持审核行为一致性的团队来说，这是一个非常有效的模式。

Codex 不应该仅仅生成代码。通过正确的指导，它还可以帮助**测试、检查和审查代码**。

如果您使用 GitHub Cloud，可以设置 Codex 来[对您的 PR 进行代码审查](/docs/third-party/github)。在 OpenAI，Codex 会审查 100% 的 PR。您可以启用自动审查，也可以让 Codex 在您 @Codex 时进行响应式审查。

## 使用 MCP 来了解外部环境

当 Codex 所需的上下文信息位于代码库之外时，请使用 MCP。它允许 Codex 连接到您已使用的工具和系统，这样您就无需不断地将实时信息复制粘贴到提示符中。

[模型上下文协议](/docs/extend/mcp)(MCP) 是一种开放标准，用于将 Codex 连接到外部工具和系统。

在以下情况下使用 MCP：

- 所需的上下文信息存在于代码库之外。
- 数据频繁变化
- 你希望 Codex 使用工具而不是依赖粘贴的指令。
- 你需要跨用户或项目的可重复集成

Codex 同时支持 STDIO 和 Streamable HTTP 服务器以及 OAuth。

在 ChatGPT 桌面应用中，前往**“设置”>“MCP 服务器”**即可查看自定义服务器和推荐服务器。通常情况下，Codex 可以帮助您安装所需的服务器。您只需提出请求即可。您也可以使用`codex mcp add`CLI 命令添加自定义服务器，并指定服务器名称、URL 和其他详细信息。

只有当工具能够真正提升工作流程时，才添加它们。不要一开始就把所有常用的工具都集成进去。先从一两个能够明显简化你经常执行的手动操作的工具入手，然后再逐步扩展。

## 将重复性工作转化为技能

一旦工作流程变得可重复，就不要再依赖冗长的提示或反复的沟通。使用[技能](/docs/build-skills)将指令`SKILL.md`、上下文和支持逻辑打包到一个文件中，Codex 应该始终如一地应用这些逻辑。这些技能可在命令行界面 (CLI)、集成开发环境 (IDE) 扩展和 ChatGPT 桌面应用程序中使用。

每项技能都应限定于一项工作。首先列出 2 到 3 个具体的用例，明确定义输入和输出，并撰写描述，说明该技能的功能和适用场景。同时，也要包含用户实际会使用的触发短语。

不要试图一开始就考虑到所有极端情况。先从一个具有代表性的任务入手，确保它运行良好，然后将该工作流程培养成一项技能，并在此基础上不断改进。只有当脚本或额外资源能够提高可靠性时，才应该添加它们。

一个很好的经验法则是：如果你不断重复使用相同的提示或纠正相同的工作流程，那么它很可能就会成为一项技能。

技能对于以下重复性工作尤其有用：

- 日志分类
- 发布说明撰写
- 根据清单进行公关审查
- 移民规划
- 遥测或事件摘要
- 标准调试流程

技能`$skill-creator`是搭建技能初始版本的最佳起点。在迭代过程中，请将初始版本保留在本地。当技能准备好广泛分享时，将其打包成[插件](https://developers.openai.com/plugins/build/plugins)。技能最重要的部分之一是描述。描述应该说明技能的功能以及何时使用。

个人技能存储在代码库中`$HOME/.agents/skills`，共享的团队技能也可以在代码库中检出`.agents/skills`。这对于新团队成员的入职培训尤其有帮助。

## 使用定时任务处理重复性工作

工作流程稳定后，您可以设置 Codex 在后台自动运行。在 ChatGPT 桌面应用中，您可以通过[计划任务](/docs/automations)选择项目、提示、频率和执行环境，以进行重复性工作。

**在“计划任务”**页面创建计划任务。选择项目、提示、频率，以及任务是在专用 Git 工作树中运行还是在本地环境中运行。提示可以调用技能。了解更多关于 [Git 工作树的](/docs/environments/git-worktrees)信息。

优秀候选人包括：

- 总结最近的提交
- 扫描可能存在的错误
- 起草发布说明
- 检查 CI 故障
- 制作站立演讲摘要
- 按计划运行可重复的分析工作流程

一条实用的原则是：技能决定方法，而计划任务决定进度。如果工作流程仍然需要大量指导，首先将其转化为一项技能。一旦工作流程变得可预测，安排进度就能节省时间。

利用计划任务进行反思和维护，而不仅仅是执行。回顾最近的聊天记录，总结反复出现的摩擦点，并随着时间的推移改进提示、说明或工作流程设置。

## 组织长时间的聊天

聊天记录会随着时间的推移积累上下文、决策和行动，因此，妥善管理聊天记录对聊天质量有很大的影响。

ChatGPT 桌面应用程序允许您置顶聊天并创建工作树。如果您使用命令行界面 (CLI)，以下[斜杠命令](/docs/developer-commands?surface=cli)尤其有用：

- `/experimental`切换实验性功能并添加到您的`config.toml`
- `/resume`恢复已保存的聊天
- `/fork`在保留原始聊天记录的同时创建新的聊天记录
- `/compact`当聊天内容过长，你想快速了解之前的内容时，Codex 可以自动压缩聊天记录。
- `/agent`当您运行并行代理并希望在活动代理线程之间切换时
- `/theme`选择语法高亮主题
- `/apps`直接在 Codex 中使用 ChatGPT 应用
- `/status`检查当前会话状态

每个连贯的工作单元都应保留一个聊天记录。如果工作仍然是同一个问题的一部分，那么留在同一个聊天记录中通常更好，因为这样可以保留推理过程。只有当工作真正出现分支时才创建分支。

使用 Codex 的[子代理](/docs/agent-configuration/subagents)工作流将有限的工作从主线程中卸载出来。让主代理专注于核心问题，并使用子代理来执行探索、测试或分类等任务。

## 常见错误

初次使用 Codex 时应避免以下几个常见错误：

- 用繁琐的规则堆砌提示，而不是将它们移入`AGENTS.md`技能中
- 不提供如何最佳运行构建和测试命令的详细信息，导致代理程序无法看到其工作成果。
- 跳过对多步骤复杂任务的规划
- 在您了解工作流程之前，请授予 Codex 对您计算机的完全权限。
- 不使用 Git 工作树，在同一文件上运行实时任务
- 在任务可靠之前手动安排重复性任务。
- 把 Codex 当作需要一步一步观看的东西来对待，而不是把它与你自己的工作并行使用。
- 整个项目使用同一个聊天记录，而不是每个重要成果都使用一个聊天记录。这会导致内容臃肿，随着时间的推移，结果也会越来越差。
